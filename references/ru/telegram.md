# Telegram

Telegram-ноды: Trigger, sendMessage, sendPhoto, inline-кнопки, приём голоса/кружков.

---

## ✅ Решения

### TG-Р1. Всегда отключать подпись n8n

- **Контекст:** по умолчанию Telegram-ноды добавляют «This message was sent automatically
  with n8n».
- **Решение:** во всех Telegram-узлах ставить `appendAttribution: false`.

Статус: ✅ Правило проекта.

### TG-Р2. Дефолт parse_mode для всех текстовых нод — `HTML` + эскейп `<>&`

- **Контекст:** в любом sendMessage / sendPhoto, где текст или caption формируются
  динамически (от LLM, от пользователя, из API), нужно безопасное форматирование. Markdown
  (default) ломается на одиночных `_ * [ \``; отсутствие parse_mode тоже даёт Markdown
  (см. TG-О1).
- **Решение:**
  1. Ставить `parse_mode: "HTML"` (snake_case!) во ВСЕХ Telegram-нодах с текстом или caption.
  2. Везде, где в text/caption может попасть пользовательский ввод или ответ LLM —
     **обязательно** прогонять через эскейп:
  ```js
  const esc = s => String(s||'').replace(/&/g,'&amp;').replace(/</g,'&lt;').replace(/>/g,'&gt;');
  ```
  3. Если LLM сама пишет текст с HTML-разметкой — явно потребовать в системном промпте:
     разрешены только `<b>`/`<i>`/`<u>`/`<s>`/`<a href="...">`/`<code>`/`<pre>`/
     `<tg-spoiler>`/`<blockquote>`; теги сбалансированы; в обычном тексте —
     `&amp;`/`&lt;`/`&gt;`.
- **Что покрывает:** `_` и `*` в `@username`, `@channel_name` не сломают пост; произвольная
  пользовательская тема `что < 10` после `esc()` уйдёт как `что &lt; 10`;
  LLM-генерированный пост с `<b>заголовок</b>` рендерится жирным.

Статус: ✅ Подтверждено в проде.

### TG-Р3. Индикатор «печатает…» (sendChatAction) — ставить так, чтобы не потерять данные

- **Контекст:** показать пользователю «печатает…», пока бот думает (особенно перед долгой
  LLM-нодой).
- **Настройка ноды:** Telegram-нода, `operation: sendChatAction`, `chatId: ={{ $json.chat_id }}`
  (из нормализующей Set-ноды прямо перед ней).
- **Обвязка (ГЛАВНОЕ):** нода `sendChatAction` **затирает текущий item** ответом Telegram API
  (см. TG-О4). Два рабочих варианта:
  1. Все ноды **после** Send Typing берут данные не из `$json`, а из upstream-ноды по имени:
     `$('Normalize').first().json.<поле>`.
  2. Либо ставить Send Typing в **боковую (тупиковую) ветку**, чтобы основной поток данных
     её не проходил.
- **Примечание (поведение Telegram API):** статус «печатает…» держится ~5 секунд и гаснет
  сам. Для длинных ответов его пришлось бы слать повторно.

Статус: ✅ Подтверждено.

### TG-Р4. Inline-кнопки и forceReply в Telegram-ноде (sendMessage)

- **Контекст:** прикрутить inline-клавиатуру (callback или URL-кнопки) либо запросить ответ
  через ForceReply.
- **Решение:**
  - Inline-клавиатура: `parameters.replyMarkup = "inlineKeyboard"`, далее
    `parameters.inlineKeyboard.rows = [{ "row": { "buttons": [ ... ] } }]`. Каждая кнопка:
    `{ "text": "...", "additionalFields": { ... } }`.
    - callback-кнопка: `additionalFields.callback_data` (**snake_case!**).
    - URL-кнопка (в т.ч. deep-link `t.me/<bot>?start=<payload>`): `additionalFields.url`.
  - ForceReply: `parameters.replyMarkup = "forceReply"`,
    `parameters.forceReply = { "force_reply": true }`.
  - camelCase (`callbackData`, `forceReply:true`) n8n молча проглатывает → кнопка не появится
    (DEP-О4). После PUT — GET-сверка, что ключи на месте.
  - answerCallbackQuery: `resource:"callback"`, `operation:"answerQuery"`, `queryId` из
    `$('<нода с апдейтом>').first().json.<cb_id>`.

Статус: ✅ Структура сверена через GET (camelCase отбрасывается, snake_case сохраняется).

### TG-Р4*. Цикл согласования (превью с кнопками + правки текстом/голосом) через статусную машину Postgres

**Контекст.** Нужен human-in-the-loop: бот показывает результат, владелец жмёт кнопки
(одобрить/доработать), правки можно прислать текстом ИЛИ голосовым. Нода «Send and Wait» не
подходит: free-text она принимает через веб-форму n8n, а не сообщением в чате, голос не
принимает вовсе.

**Решение** (✅ подтверждено в проде):

1. **Состояние — таблица в Postgres** (`<bot>_drafts`, ключ `chat_id`, колонка `stage` +
   данные черновика). Каждое сообщение/кнопка = новый запуск воркфлоу; стадия определяет
   маршрут. Переживает рестарты n8n, ожидание бессрочное, исполнения короткие.
2. **Trigger updates = `["message","callback_query"]`**. Check Access и chatId — через
   `COALESCE`: `message?.from?.id || callback_query?.from?.id`.
3. **Загрузка состояния всегда 1 строкой** (иначе ветка без items не сработает):
   `SELECT COALESCE(d.stage,'') ... FROM (SELECT 1) x LEFT JOIN <bot>_drafts d ON d.chat_id = {{ Number(...) }}`.
4. **Маршрутизатор (Switch, loose v2)**: сначала callback_data кнопок (string equals), потом
   `/start`, потом стадии ожидания ввода (regex по stage + наличие message), потом новый
   запрос (text/caption не пуст), fallback — вежливый отказ.
5. **Кнопки** — обычный sendMessage с `replyMarkup: inlineKeyboard`. На каждую callback-ветку
   первой нодой — `resource: callback` (answerQuery, `queryId = callback_query.id`), иначе на
   кнопке висит спиннер.
6. **Голос только в точках ожидания**: IF `!!message?.voice` → Telegram `resource: file`
   (voice.file_id) → openAi `resource: audio, transcribe, language: ru` → общий Code «Входной
   текст» → Switch по стадии. Вне стадий голос отклоняется.
7. **Текстовые значения в SQL** — инлайн-литералом с эскейпом кавычек:
   `'{{ expr.replace(/'/g, "''") }}'` (queryReplacement ломается на запятых в тексте). Все
   UPDATE — с `RETURNING *`.
8. Завершение — не DELETE, а `stage='published'`: следующий запрос перезапишет строку через
   UPSERT.

### TG-Р5. Приём видео-кружков (video_note) наравне с голосовыми

**Контекст.** Бот должен принимать не только voice, но и видео-кружки (video_note) и
использовать их как голосовой ввод (расшифровка аудиодорожки).

**Решение** (✅ подтверждено в проде):

1. **Детект** — в IF/Switch проверять оба типа:
   `!!($json.message?.voice || $json.message?.video_note)`.
2. **Скачивание** — Telegram-нода `resource: file`,
   `fileId = {{ message.voice?.file_id || message.video_note?.file_id }}` (один узел для обоих).
3. **Расшифровка** — openAi `resource: audio, operation: transcribe, language: ru` принимает
   mp4-кружок **напрямую**, извлекать аудиодорожку отдельно не нужно.
4. Дальше — общий код «Входной текст», как для voice (TG-Р4* п.6).

**Защита черновика при свободном голосе/кружке.** Если голос/кружок может прийти и как «новый
интент» (без активного черновика), и как правка (в стадии ожидания) — в правиле «новый интент»
добавить второе условие по stage: срабатывать только когда черновика нет (`stage`
пустой/`published`/`cancelled`). Иначе случайное голосовое при готовом превью затрёт черновик.

### TG-Р6. Retry On Fail на Telegram-нодах отправки (защита от транзиентных сбоев)

**Контекст.** Внешние Telegram-вызовы (sendMessage / sendPhoto / sendChatAction / getFile)
изредка падают транзиентно — например, спорадический «chat not found» при валидном конфиге
(TG-О7) или сетевой блип. Один такой сбой роняет весь прогон и теряет сообщение / уведомление /
лид.

**Решение.** На Telegram-нодах отправки и скачивания включать **node-level** retry:
`retryOnFail: true`, `maxTries: 3`, `waitBetweenTries: 5000` (это поля самой ноды, не в
`parameters`).

**⚠️ Исключение — публичная публикация.** Retry даёт семантику **at-least-once**: если Telegram
доставил сообщение, но ответ до n8n не дошёл (обрыв ровно между доставкой и ответом), повтор
создаст **дубль**. Для ack / ответов юзеру / уведомлений владельцу / скачиваний файлов дубль
терпим. Для нод, постящих в **публичный канал/ленту** (например нода «Опубликовать в Telegram»),
retry **НЕ включать** — дубль = двойной публичный пост.

**Деплой.** Выставить три поля на ноде, PUT, затем GET-сверка что `retryOnFail` сохранился.
Кредитные привязки при этом не трогаются (на текущем инстансе GET возвращает `credentials` —
достаточно прокинуть их без изменений).

**Источник.** Рассылка retry по 8 активным воркфлоу (52 Telegram-ноды отправки; публичная
публикация исключена). Исходный кейс — TG-О7.

**Статус:** ✅ Подтверждено в проде.

### TG-Р7. Картинку в Telegram слать бинарём (download → sendPhoto binaryData), не by-URL

**Контекст.** Картинка хранится по публичному URL (imgBB — он нужен для Instagram Graph API).
Для Telegram доставка ссылкой ненадёжна (TG-О8) и ограничена 5 МБ.

**Решение.** Перед Telegram-нодой вставить HTTP Request, который скачивает URL в бинарь, а
sendPhoto слать бинарём:
- HTTP Request (GET, `url={{ image_url }}`),
  `options.response.response = { responseFormat: "file", outputPropertyName: "data" }`;
  `retryOnFail` на скачивании можно (идемпотентный GET).
- Telegram sendPhoto: `binaryData: true`, `binaryPropertyName: "data"`, поле `file` НЕ задавать.
  `caption`/`parse_mode` брать из именованной ноды
  (`$('Загрузить черновик').first().json.body_text`), т.к. после HTTP в `$json` лежит бинарь,
  не текст.

Снимает оба класса ошибок TG-О8 и лимит 5 МБ (бинарь-photo до 10 МБ). imgBB остаётся для
Instagram — Graph API тянет URL на своей стороне.

**⚠️ Retry на самой публикующей sendPhoto в канал НЕ ставить** (дубль, TG-Р6) — retry допустим
только на ноде скачивания.

**Источник.** Продукт-публикатор, «Скачать обложку» → «Финальное превью: фото» и
«Скачать обложку (публикация)» → «Опубликовать в Telegram».

**Статус:** ✅ Подтверждено в проде.

### TG-Р8. Фильтр «только приватный чат» на входе бота

**Контекст.** Бот для личного использования (владелец в ЛС). Апдейты из каналов/групп — мусор
и источник ошибок (TG-О9).

**Решение.** Сразу после Telegram Trigger (до проверки доступа и любых ответов) — IF по типу
чата:
```
chat_type = {{ ($('Telegram Trigger').item.json.message || $('Telegram Trigger').item.json.edited_message || $('Telegram Trigger').item.json.callback_query?.message || {}).chat?.type || '' }}
```
`chat_type === 'private'` → дальше; иначе → NoOp (тихо игнорировать, без ответа). Покрывает
message, edited_message и callback_query разом.

**Источник.** Продукт-публикатор, «Личный чат?».

**Статус:** ✅ Подтверждено в проде.

### TG-Р9. Реакция на правку своего сообщения (edited_message) как на новый дословный ввод

**Контекст.** Нужно дать пользователю править уже отправленный текст не новым сообщением, а
редактированием своего же (UX «поправил по месту»).

**Решение.**
1. В Telegram Trigger добавить тип апдейта `edited_message` (наравне с `message`,
   `callback_query`).
2. Везде, где читается входящее, поддержать обе ветки: `message?.… || edited_message?.…`
   (chat.id, from.id, text — в CHAT/CHATNUM, Check Access, save-нодах).
3. В маршрутизаторе: правило «есть `edited_message` И стадия = `<режим ручного ввода>`» →
   сохранить `edited_message.text` дословно → показать превью. Прочий `edited_message`
   (не в нужной стадии) → тихо игнорировать (иначе правка старого сообщения ложно триггерит).
4. Ограничение: бот может ловить правки только **своих** сообщений пользователя; первый ввод
   всё равно приходит обычным сообщением, дальше — правки. Telegram отдаёт edited_message
   только ~48 ч.

**Источник.** Продукт-публикатор, «Сохранить тексты (правка сообщения)» + правило
`edit_text_manual`.

**Статус:** ✅ Подтверждено в проде.

### TG-Р10. Мягкая обработка битого пользовательского HTML в send (onError → подсказка)

**Контекст.** Если текст для отправки формирует пользователь (ручной ввод, свой готовый пост),
его HTML может быть невалиден (`<b>…<b>` вместо `</b>`). sendMessage/sendPhoto с
`parse_mode: HTML` на таком падает (`can't find end tag …`) — нода краснеет, юзер без обратной
связи.

**Решение.** На превью-ноде (которая первой шлёт пользовательский текст с parse_mode HTML)
выставить `onError: continueErrorOutput`. Error-выход (index 1) → отдельная статичная
нода-подсказка (без тегов в тексте, чтобы сама не упала): «битая разметка, закрывающий тег —
`&lt;/b&gt;`, поправь и пришли ещё раз». Превью работает как «ворота»: пока разметка битая —
публикация недостижима, а юзер видит понятную причину. Стадию держать в «дословном» режиме,
чтобы повторная присылка осталась verbatim.

**Источник.** Продукт-публикатор, «Превью текста» (error-выход) → «Превью: битая разметка».

**Статус:** ✅ Подтверждено в проде.

### TG-Р11. Динамический список-карточки с inline-кнопками (id в callback_data через expression)

- **Контекст:** нужно показать пользователю список записей из БД (очередь постов, задачи),
  у каждой — свои кнопки действий.
- **Решение:** не строить одну общую клавиатуру, а слать **карточку на каждый item**:
  Postgres-нода возвращает N строк → Telegram-нода исполняется per item. В callback_data кнопок —
  expression с id записи: `"=q_now_{{ $json.id }}"`. Обработчик-callback в маршрутизаторе ловит
  по regex (`^q_now_`), id достаёт `split('_')[2]`.
- **Плюсы:** нет возни с динамической сборкой reply_markup JSON; каждая карточка
  самодостаточна; действия атомарны по id (UPDATE ... WHERE id AND status — защита от
  устаревших кнопок).
- **Пустой список:** Postgres при 0 строк отдаёт `{success:true}` (PG-О2) — обязателен IF-guard
  по ключевому полю перед карточкой, иначе уйдёт карточка с мусором.
- **Источник:** продукт-публикатор, команда /queue (карточки очереди с 🚀/🕒/❌).
- **Статус:** ✅ Подтверждено в проде.

### TG-Р12. Меню-кнопка бота = Web App (приложение) вместо списка команд

- **Задача:** чтобы меню-кнопка бота (внизу слева в чате) открывала Mini App, а не показывала
  список команд.
- **Решение (Bot API, без BotFather):** `POST https://api.telegram.org/bot<token>/setChatMenuButton`
  с телом `{"menu_button":{"type":"web_app","text":"Открыть","web_app":{"url":"https://<app-url>/"}}}`.
  Без `chat_id` — дефолт для всех. URL обязательно HTTPS. Вернуть как было:
  `{"menu_button":{"type":"commands"}}`.
- **⚠️ Грабля readback:** сразу после `set` (ok:true) `getChatMenuButton` может ещё отдавать
  старое (`{type:'commands'}`) — **задержка распространения Telegram**, не ошибка. Перепроверить
  через минуту: дефолт читается как `{type:'web_app',...}`, у конкретного чата —
  `{type:'default'}` (наследует дефолт). Не «чинить» повторными set'ами по первому чтению.
- **Токен:** брать из `*_config`/исполнения сервер-сайд, в чат/логи не выводить.
- **Источник:** бот-публикатор.
- **Статус:** ✅ Подтверждено в проде (кнопка открывает приложение).

### TG-Р13. Пересланное/ссылка → инбокс Mini App: детект и гейт перед роутером

- **Задача:** бот-мост должен класть пересланную новость в `pub_inbox` (→ блок «Из
  пересланного» в Mini App), а не обрабатывать её в чате.
- **Грабля 1 — детект только по `forward_date`.** Узел «Переслано?» проверял
  `!!message.forward_date`. Но когда юзер **делится ссылкой** (share-sheet/копипаст URL),
  Telegram шлёт это **обычным сообщением без единого forward-поля** (`message` =
  message_id/from/chat/date/text/entities — ни `forward_date`, ни `forward_origin`). Поэтому
  ссылка-новость не распознавалась как «пересланное». Решение: расширить условие —
  `!!m.forward_date || /^https?:\/\//i.test((m.text||m.caption||'').trim())`. (Также помнить:
  легаси `forward_from*`/`forward_date` Telegram постепенно вытесняет `forward_origin` — для
  настоящих форвардов проверять оба.)
- **Грабля 2 — детект-нода работала ПАРАЛЛЕЛЬНО роутеру.**
  `Загрузить черновик → [Маршрутизатор, Переслано?]` одновременно: даже распознанное
  пересланное всё равно шло и в роутер → при активном черновике URL «съедался» как правка
  текста. Решение: сделать детект **воротами ПЕРЕД роутером** —
  `Загрузить черновик → Переслано?`; true → инбокс; **false (output 1) → Маршрутизатор**. IF
  пробрасывает тот же item, роутер получает те же данные. Теперь форвард/ссылка идут только в
  инбокс.
- **Грабля 3 — тихая запись.** После INSERT в `pub_inbox` бот молчал → «ничего не произошло».
  Добавить ответ-подтверждение («🔗 Добавил в приложение → открой, блок «Из пересланного»»).
- **Инбокс-нода устойчива к отсутствию forward-полей:** `src` собирать с фолбэками
  (`forward_origin.chat.title || sender_user || forward_from... || ''` → «Репост»), `text` =
  `message.text||caption`. Для голой ссылки src=«Репост», text=URL — не ломается.
- **Источник:** бот-публикатор (`<workflow_id>`).
- **Статус:** ✅ Подтверждено в проде.

### TG-Р14. Вход в веб-приложение через Telegram Login Widget → сессионный HMAC-токен (secret=SHA256(token), ≠ initData)

- **Задача:** аутентифицировать пользователя в **браузерной** веб-версии Telegram-продукта
  (не Mini App) на n8n-бэкенде, затем переиспользовать те же data-эндпоинты, что и в Mini App.
- **Ключевое отличие подписи от Mini App.** Telegram отдаёт **две разные** схемы, их легко
  перепутать:
  - **Login Widget** (виджет «Log in with Telegram» на сайте): `secret = SHA256(bot_token)`
    (бинарный дайджест), `data_check_string` = все поля виджета **кроме `hash`**, отсортированы
    по ключу, `key=value`, join `\n`; `check = HMAC_SHA256(dcs, secret)` в hex == `hash`.
    Дополнительно `auth_date` ≤ 86400 c (анти-replay).
  - **Mini App initData** (см. TG-О11): `secret = HMAC_SHA256("WebAppData", bot_token)`.
    **Не взаимозаменяемы.**
- **Сессия вместо повторной валидации.** Подпись виджета валидна один раз (виджет не
  присылается на каждый запрос). После успешного `auth/telegram` бэкенд выдаёт
  **самодостаточный сессионный токен** без серверной таблицы сессий:
  `base64url(JSON{telegram_id,exp}) + "." + base64url(HMAC_SHA256(payload, SESSION_SECRET))`.
  Срок (`exp`) — напр. 30 дней. Дальше каждый запрос несёт токен; бэкенд проверяет подпись +
  `exp` и берёт `user_id` **из токена, никогда из payload** (защита от подмены).
- **`SESSION_SECRET` — в БД-конфиге** (таблица `*_config`, отдельный ключ), читается нодой
  `Load Config` в начале воркфлоу; в код/ответы/логи не попадает. Один секрет на инстанс,
  сгенерирован разово.
- **Переиспользование запросов.** После гейта по токену те же Postgres-запросы, что и в Mini
  App (профиль, факты, история, дневник, награды), обслуживают веб — изоляция достигается
  **дублированием SQL в отдельном воркфлоу** (`<workflow_name>`), без общих нод с
  miniapp/основным ботом.
- **Гейт доступа** — общий `bot_access(bot='<slug>', active=true)` по `telegram_id` из
  проверенной подписи; нет доступа → токен не выдаётся (пустая строка), фронт показывает «нет
  доступа».
- **Источник:** продукт-коуч, `<workflow_name>` (webhook `<webhook_path>`, id `<workflow_id>`).
- **Статус:** ✅ Подтверждено в проде (валидный hash → токен; поддельный/просроченный → 401).

### TG-Р15. Безопасный прокси аватара Telegram — подписанный URL, токен бота не на клиенте

- **Задача:** показать настоящий аватар пользователя из Telegram в вебе/Mini App, **не
  раскрывая токен бота** клиенту (URL файла Telegram содержит токен в пути).
- **Решение — отдельный прокси-воркфлоу с подписанным URL:**
  1. Эндпоинт `GET /webhook/<webhook_path>?uid=<telegram_id>&sig=<подпись>`, где
     `sig = HMAC_SHA256(String(uid), AVATAR_SECRET)` в hex. Неверная/отсутствующая подпись →
     **403**. Подпись генерит основной API при выдаче `photo_url` — клиент не может подделать
     `uid`.
  2. По валидной подписи: Bot API `getUserProfilePhotos(user_id=uid, limit=1)` → берём самый
     большой размер (последний элемент `photos[0]`) → `file_id` → `getFile` → `file_path` →
     скачивание `https://api.telegram.org/file/bot<token>/<file_path>` (HTTP-нода, response=file)
     → **отдаём байты** (`image/jpeg`).
  3. Кэш: ответ с `Cache-Control: public, max-age=86400`. Нет фото / приватность / ошибка Bot
     API → **404** (фронт показывает заглушку через `onerror`).
- **Безопасность:** `bot_token` и `AVATAR_SECRET` — из `*_config` (нода `Load Config`), в
  ответ/редирект/заголовки/логи не попадают. Скачивание целиком на стороне n8n → наружу уходят
  только байты картинки, не URL с токеном. HTTP-ноды к Bot API: `retryOnFail` 3×5с,
  `getUserProfilePhotos`/`getFile` с `onError: continueRegularOutput` (мягкая деградация в 404).
- **Единообразие:** в Mini App тоже отдавать прокси-URL, а не `initData.photo_url` — один
  код-путь на фронте + всегда свежая кэшируемая картинка.
- **Источник:** продукт-коуч, `<workflow_name>` (webhook `<webhook_path>`, GET, id
  `<workflow_id>`).
- **Статус:** ✅ Подтверждено в проде (валидная подпись → 200 image/jpeg 640×640; битая → 403;
  токена в ответе нет).

### TG-Р16. Зеркалирование канала — исходящий sendMessage из веб-ветки в Telegram-диалог не создаёт петли

- **Задача:** переписка пользователя с агентом **с сайта** должна быть видна и в его
  Telegram-чате с ботом (единый диалог через два канала).
- **Решение:** после того как веб-ветка сформировала ответ, **параллельно** веб-ответу слать в
  Telegram два `sendMessage` от имени бота: эхо сообщения пользователя (с пометкой канала, напр.
  `🌐 <Имя> (с сайта):\n<текст>`) + ответ агента. Имя — из `profile.name` по `telegram_id` (тем
  же запросом, что грузит промт/профиль — без отдельной ноды).
- **Почему петли нет:** исходящий `sendMessage` **бота** не порождает входящий update в Telegram
  Trigger (бот не «слышит» сам себя) → основной воркфлоу не запускается. Зеркалирование
  безопасно односторонне.
- **Надёжность (важно):** ветка зеркала идёт **параллельно** ноде веб-ответа
  (`Respond to Webhook` отвечает первым и независимо). HTTP-ноды Telegram —
  `onError: continueRegularOutput` + `retryOnFail` 3×5с: **сбой Telegram не ломает веб-ответ** и
  не роняет исполнение. Память диалога **не дублируется** — её пишет нода памяти агента в
  основном проходе; зеркало только шлёт в Telegram.
- **Форматирование переиспользуется** из основного бота (`stripLeak` + конвертация сентинела
  `⟪PROGRAM⟫`→`<blockquote expandable>`, `parse_mode=HTML` только при наличии блока). Брать
  **сырой вывод агента**, а не уже «очищенный» для веба (если очистка срезает сентинелы). Нет
  токена/`user_id` → нода возвращает `[]` (зеркало пропускается).
- **Источник:** продукт-коуч, `<workflow_name>` ветка `chat/send`
  (`Web Mirror Format`/`Mirror Echo`/`Mirror Reply`).
- **Статус:** ✅ Принято на проде (логика проверена; реальная доставка — из живой веб-сессии, за
  владельцем).

## ⚠️ Ошибки

### TG-О1. `parse_mode: ""` не отключает Markdown

- **Симптом:** хочешь отправить «сырой» текст, ставишь `parse_mode: ""` — а Telegram всё
  равно парсит Markdown, текст приходит с разметкой/ломается на спецсимволах.
- **Причина:** пустая строка не воспринимается как «без форматирования».
- **Лечение:** ставить `parse_mode: "HTML"` (а не пустую строку и не Markdown). Вскрыто за
  4 пинга через sandbox-верстак (см. debugging-sandbox.md DBG-Р1).

### TG-О2. sendPhoto — параметр `file`, не `photo`; parse_mode в snake_case

- **Симптом:** настраиваешь отправку фото через API, фото не уходит / параметр игнорируется.
- **Причина:** в n8n-ноде Telegram параметр для фото называется `file`, а не `photo`. Имена
  чувствительны: `parse_mode` пишется в snake_case. Неверное имя n8n молча выбрасывает
  (см. rest-api-deploy.md DEP-О4).
- **Лечение:** использовать `file`; parse_mode — snake_case; после PUT делать GET-сверку.

### TG-О3. Подпись «sent automatically with n8n» в сообщениях

- **Симптом:** в сообщениях бота снизу приписка про n8n.
- **Причина:** не выставлен `appendAttribution: false`.
- **Лечение:** см. TG-Р1.

### TG-О4. После sendChatAction («Send Typing») downstream теряет chat_id/message_id/text

- **Симптом:** после ноды Telegram `sendChatAction` следующие ноды получают `undefined`
  вместо `chat_id` / `message_id` / `text`. Запросы в БД пишут null, ответы уходят не туда.
- **Причина:** Telegram-нода (как и большинство action-нод n8n) **заменяет текущий item своим
  ответом API** — после неё `$json` это примерно `{ "result": true }`, а не данные из
  нормализующей ноды.
- **Лечение:** в нодах после Send Typing ссылаться на upstream по имени —
  `$('Normalize').first().json.<поле>`, а не `$json.<поле>`. Либо вынести Send Typing в
  боковую ветку. Паттерн целиком — TG-Р3.

### TG-О5. Подстановка `{{ }}` в тексте ноды приходит сырым текстом

- **Симптом:** в сообщении бота вместо значения видно буквально `{{ $json.foo }}`. Хуже —
  ломается downstream-логика, которая ищет подставленный маркер.
- **Причина:** n8n трактует строковое поле как **выражение** только если оно начинается с `=`.
  Текст с `{{ }}` без ведущего `=` уходит литералом. Легко забыть на статичных текстах, где
  подстановка лишь в середине.
- **Лечение:** любое поле (`text`, `chatId`, `callback_data`, `url`), содержащее `{{`, должно
  начинаться с `=`. В генераторе — хелпер:
  `'=' + v if '{{' in v and not v.startswith('=') else v`. После PUT — GET-сверка.

### TG-О6. «Bad Request: chat not found» при sendMessage + правило выбора бота

- **Симптом.** Telegram-нода sendMessage падает с `Bad request - please check your parameters`,
  в `description` — `Bad Request: chat not found`. Credential при этом валиден (ошибки
  «Credential … does not exist» нет).
- **Причина.** Бот, на котором висит credential, физически не может написать этому `chatId`,
  потому что пользователь **никогда не нажимал Start / не писал этому боту**. Личный чат с ботом
  возникает только после того, как человек первым написал боту. Это НЕ ошибка параметров —
  Telegram просто не знает такого чата для данного бота. У каждого бота — свой отдельный личный
  чат.
- **Лечение.** Открыть нужного бота в Telegram и отправить ему любое сообщение (Start). После
  этого sendMessage на этот chatId проходит. Запускать надо именно того бота, чей credential
  стоит в ноде.
- **Сопутствующее правило.** При сборке Claude по своей инициативе подключил к уведомлениям
  чужой бот (бот-консультант) — так нельзя. **Перед подключением ЛЮБОГО бота/credential к
  воркфлоу — всегда спрашивать, какой именно бот использовать. Не выбирать по догадке и не
  переиспользовать чужой бот.** Один бот = один Telegram Trigger (webhook): переиспользование
  триггерного бота в другом сценарии ломает исходный.
- **Статус:** ⚠️ Зафиксировано.

### TG-О7. Спорадический «chat not found» при полностью валидном конфиге (транзиент Telegram)

- **Симптом.** sendMessage падает с `Bad Request: chat not found`, но конфиг исправен и **тот же
  бот в тот же чат успешно пишет в соседних прогонах**. Отличается от TG-О6: там бот не запущен
  пользователем — падает всегда детерминированно; здесь сбой разовый.
- **Признак транзиента.** 2 из 3 идентичных прогонов (тот же `chatId`, тот же бот, та же нода,
  отличался лишь URL inline-кнопки, который Telegram на существование не проверяет) — успешны,
  один упал.
- **Лечение.** Не искать «баг параметров» — его нет. Включить node-level Retry On Fail (см.
  TG-Р6). Один транзиентный сбой не должен ронять весь воркфлоу и терять лид/уведомление.
- **Статус:** ⚠️ Зафиксировано.

### TG-О8. sendPhoto by-URL с imgBB: «failed to get HTTP URL content» / «wrong type of the web page content»

- **Симптом.** Telegram-нода sendPhoto с `file = {{ image_url }}` (ссылка на `i.ibb.co/.../*.png`)
  падает: либо `Bad Request: failed to get HTTP URL content` (Telegram не смог скачать), либо
  `Bad Request: wrong type of the web page content` (скачал не то). Спорадически: одна генерация
  проходит, следующая — нет.
- **Причина.** Доставка картинки **ссылкой** перекладывает скачивание на Telegram. imgBB-CDN
  сразу после загрузки «холодный» (даёт первый класс ошибки) или отдаёт контент так, что
  Telegram не распознаёт image-тип (второй класс). Плюс photo-by-URL имеет лимит 5 МБ — тяжёлый
  PNG его пробивает.
- **Лечение.** Не давать Telegram тянуть URL — скачивать картинку в воркфлоу и слать **бинарём**
  (multipart). См. TG-Р7. Retry by-URL не лечит «wrong type» (это не прогрев CDN, а сам способ
  доставки).
- **Источник.** Продукт-публикатор, «Финальное превью: фото» / «Опубликовать в Telegram».
- **Статус:** ⚠️ Зафиксировано.

### TG-О9. Апдейт из канала/супергруппы → «channel direct messages topic must be specified»

- **Симптом.** Бот, рассчитанный на личку, получает апдейт с отрицательным `chat.id`
  (канал/супергруппа). Ветка ответа (sendMessage в этот chat) падает: `Bad Request: channel
  direct messages topic must be specified` (новая фича Telegram «channel direct messages»).
- **Причина.** Триггер ловит сообщения не только из лички. Подписка на `edited_message`/
  нахождение бота в группе расширяет поток входящих. Ответ в канал без указания topic Telegram
  отвергает.
- **Лечение.** Фильтровать вход по типу чата. См. TG-Р8.
- **Источник.** Продукт-публикатор, «Отказ в доступе».
- **Статус:** ⚠️ Зафиксировано.

### TG-О10. `require('crypto')` запрещён в Code-нодах этого инстанса — HMAC/SHA256 только pure-JS

- **Симптом:** Code-нода, делающая подпись/проверку (HMAC-SHA256, SHA256 — валидация Login
  Widget/initData, подпись прокси-URL, сессионный токен), падает на `require('crypto')` (модуль
  не доступен в песочнице Code-ноды этого n8n). Любая крипто-логика через стандартный `crypto`
  не запускается.
- **Причина:** в настройках этого инстанса встроенные Node-модули в Code-нодах не разрешены
  (`NODE_FUNCTION_ALLOW_BUILTIN` не включает `crypto`).
- **Лечение:** реализовать SHA-256 и HMAC-SHA256 **чистым JS** (без `require`) и переиспользовать
  один и тот же блок во всех крипто-нодах (валидация подписи, выдача/проверка токена, подпись
  аватар-URL). В продукте-коуче pure-JS реализация перенесена между воркфлоу (initData) и
  веб-воркфлоу (Login Widget + сессия + подпись URL) копированием.
- **Профилактика:** при любой новой крипто-задаче в Code-ноде — сразу брать готовую pure-JS
  реализацию из соседнего воркфлоу, не писать `require('crypto')` «как на бэкенде». Проверять на
  исполнении (ошибка видна в runtime, не в конфиге).
- **Источник:** продукт-коуч, ноды `Auth`/подпись (перенос между воркфлоу).
- **Статус:** ⚠️ Подтверждено на проде (pure-JS работает, `require('crypto')` — нет).

### TG-О11. Подпись Mini App initData для теста: компактный JSON + `%20`, не `+`

- **Контекст:** чтобы проверить вебхук-бэкенд Mini App без Telegram (curl с поддельным, но
  валидно подписанным `initData`), подпись считается двойным HMAC-SHA256:
  `secret = HMAC("WebAppData", bot_token)`, `hash = HMAC(secret, data_check_string)`, где
  `data_check_string` — пары `k=v` (без `hash`), отсортированы, через `\n`, значения **в
  URL-декодированном виде**.
- **Грабли:** (1) поле `user` сериализовать **компактным** JSON без пробелов
  (`separators=(",",":")`) — иначе строка не совпадёт с тем, что n8n получит после
  decodeURIComponent; (2) при сборке query кодировать пробелы как `%20`, **не `+`**
  (`urlencode(..., quote_via=quote)`): n8n использует `decodeURIComponent`, который `+` в пробел
  не превращает → `data_check_string` разъезжается → hash mismatch → 401.
- **Также:** гейт «только админ» проверять по `id` из **подписанного** `initData.user`, не из
  payload; `auth_date` не старше 24ч.
- **Источник:** продукт контроля доступа, Mini App API — smoke-тест 401/200.
- **Статус:** ⚠️ Подтверждено (подписанные запросы → 200, чужой/битый/пустой → 401).
