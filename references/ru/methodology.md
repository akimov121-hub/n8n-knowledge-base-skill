# Методология ведения n8n-проекта

Рабочие правила организации, именования, архитектуры и протоколов для self-hosted n8n.
Это best-practices, выработанные на практике; адаптируй под свою команду.

---

## 1. Структура проекта

**Один сценарий — одна папка.** Все файлы по сценарию (workflow.json, промты, описание)
хранятся в отдельной подпапке. Правило действует всегда — даже если файл единственный, даже
для мелкой доработки, даже для новой версии (v2, v3 кладутся в ту же папку). Никогда не
сваливать файлы сценариев в корень.

**Плоская структура внутри папки сценария.** Все артефакты на одном уровне. Вложенность
оправдана только для связки из нескольких сценариев (AI-агент с инструментами, мастер + суб).

**Песочница.** Sandbox-воркфлоу живут в общей папке `sandbox/<имя>/`, каждый в своей подпапке,
с собственным описанием. После сессии тестов — деактивировать (см. debugging-sandbox.md).

```
/проект
├── CLAUDE.md / README             ← правила проекта
├── _Index.md                      ← карта всех сценариев (если ведёшь vault)
├── [Имя сценария]/
│   ├── Описание [Имя].md          ← цель, архитектура, файлы, история разработки
│   ├── workflow.json              ← последний экспорт из n8n
│   ├── system-prompt.md           ← системный промпт (если есть AI-нода)
│   └── changelog.md               ← история версий
└── sandbox/
    └── [Имя sandbox]/
```

## 2. Именование

**Воркфлоу:** формат `[Клиент/Сфера] — [Действие]`. Примеры: `Строительство — Напоминания о
дедлайнах`, `Входящие лиды — Квалификация + CRM`. Версии: `v2`, `v3` в конце.

**Папки сценариев:** имя дословно совпадает с именем воркфлоу. Имя по назначению, не по каналу
доставки (никаких префиксов `TG-`, `WA-`). Переименование папки — атомарная операция:
одновременно переименовать папку, файл описания, запись в индексе и все ссылки.

**Ноды внутри воркфлоу:** осмысленные имена (не `HTTP Request`, а `Получить данные из 1С`).
Порядок слева направо = порядок выполнения.

**Credentials:** формат `[Сервис] — [Назначение/Клиент]`. Примеры: `Telegram Bot —
Уведомления`, `OpenAI — Основной`, `PostgreSQL — Prod`.

## 3. Sticky Note — визитка воркфлоу

**Обязательна в каждом воркфлоу** (включая суб- и tool-воркфлоу). Создаётся первой. Это первое,
что видишь при открытии сценария.

- `type`: `n8n-nodes-base.stickyNote`, `color`: `5` (оранжевый), `width`: `360`, `height`: `216`.
- Позиция: левее и чуть выше trigger-ноды (x = trigger_x − 400, y = trigger_y − 20).

Формат содержимого (4–5 строк, не дублировать файл описания):

```
## [Имя воркфлоу]
[Одна фраза: что делает и для кого.]
[Ключевые акторы / точки входа: кто или что триггерит.]
[Интеграции и таблицы, с которыми работает.]
[Особые ограничения или предупреждения, если есть.]
```

Если сценарий дорогой (LLM/изо-генерация) — добавить `⚠️ Дорогой прогон — отлаживать через
sandbox.` Визитку обновлять молча при: новом канале ввода, новой интеграции, новом credential,
смене ключевой логики, переименовании, переводе в Production.

## 4. Файлы описания сценариев

В каждой папке — `Описание [имя].md`. Содержит: суть (1–2 предложения); таблицу «что в папке»;
триггер и условия запуска; описание ключевых нод и потока данных (с ASCII-диаграммой, если нод
> 5); зависимости (credentials, внешние сервисы); **историю разработки** (источник, что сделали,
трудности и как решили, что отложено); статус (Draft / Testing / Production).

История разработки обязательна, если сценарий портирован из другого инструмента, были
нетривиальные решения, или часть функциональности отложена.

## 5. Архитектурные принципы

- **Один воркфлоу — одна ответственность.** Лучше 3 простых, чем 1 запутанный.
- **Модульность через суб-воркфлоу.** Повторяемую логику (форматирование уведомлений,
  валидация, запрос к конкретному API) выносить в отдельный воркфлоу (Execute Sub-workflow).
- **Error Workflow обязателен** для каждого продакшн-воркфлоу. Стандартная цепочка:
  `Error Trigger → Edit Fields (форматирование) → Telegram (уведомление)`. Содержит: название
  упавшего воркфлоу, ID ноды, сообщение ошибки, timestamp.
- **Retry для нестабильных API.** На внешних HTTP-запросах `Retry On Fail`: 3 попытки, 5 сек.
- **Валидация на входе.** После Webhook/Form-триггера первой нодой — IF на обязательные поля.
  При отсутствии — понятная ошибка + Stop And Error.

## 6. Работа с данными (шпаргалка по expressions)

```
{{ $json.name }}                            — поле из текущего item
{{ $node["Имя ноды"].json.field }}          — поле из конкретной ноды
{{ $('Имя ноды').first().json.field }}      — безопасный cross-node ref (см. AI-О1)
{{ DateTime.now().toFormat('dd.MM.yyyy') }} — дата
{{ $input.all().length }}                   — количество items
{{ $runIndex + 1 }}                         — номер итерации с 1
{{ JSON.stringify($json) }}                 — весь item как строка
```

Типичные трансформации: переименовать/добавить поля → Edit Fields (Set); отфильтровать →
Filter; убрать дубли → Remove Duplicates; разбить по порциям → Split In Batches; объединить
ветки → Merge; агрегировать → Aggregate / Summarize.

## 7. Структура AI-агента (типовая)

```
Webhook/Chat → AI Agent
                 ├── Chat Model (LLM)
                 ├── Memory (Postgres Chat Memory)
                 └── Tools:
                       ├── HTTP Request Tool (внешние API)
                       ├── Workflow Tool (суб-воркфлоу)
                       └── Vector Store Tool (RAG)
```

RAG-паттерн:
```
[Загрузка] → Document Loader → Text Splitter → Embeddings → Vector Store
[Запрос]   → Webhook → AI Agent + Vector Store Tool → Ответ
```

Подробности по памяти, выбору модели и RAG без векторов — в ai-agents.md.

## 8. Протокол «сначала план — потом сборка за один заход»

Для портирования сценариев (Make/Zapier → n8n) и любой крупной/нетривиальной задачи. Этапы
строго последовательны:

1. **Изучить исходные материалы** — все переданные файлы и текущее состояние n8n. Ничего не
   предлагать, пока не прочитано всё.
2. **Составить детальный план** — для портирования таблица «модуль источника → нода n8n»;
   для нового сценария архитектура нод слева направо.
3. **Предложить решения по каждому узлу** и явно вынести точки принятия решений: выбор модели,
   тип памяти, обработка ошибок и пустых ответов, источник ключа сессии, cutover, разграничение
   доступа, 152-ФЗ.
4. **Согласовать с заказчиком** — задать уточняющие вопросы, дождаться явного согласия.
5. **Собрать за один заход** — только после согласия: создать папку и файлы, задеплоить,
   прогнать smoke-test.

Не начинать сборку до явного «делаем». Этап обсуждения — это и есть работа.

## 9. Финализация после подтверждения «работает»

Когда заказчик подтвердил, что сценарий финально работает — выполнять молча, не дожидаясь
отдельной просьбы:

1. **Зафиксировать переиспользуемое решение** в картотеке (статус ✅, теперь можно).
2. **Снять локальные снимки ВСЕХ воркфлоу связки** (не только изменённых): пере-экспорт из
   live, восстановить `credentials` по node id (GET их не отдаёт), сохранить в папку. Папка —
   цельный актуальный снимок связки.
3. **Синхронизировать описание и индекс.**
4. **Кратко отписать, что именно сделано** — какие решения записаны, какие снимки обновлены.

Промежуточные «ок, дальше», «понятно» в ходе обсуждения — НЕ сигнал финализации.

## 10. Безопасность

- **⛔ Не удалять/необратимо менять ДАННЫЕ без явного разрешения.** `DELETE`, `DROP`,
  `TRUNCATE`, разрушительный `UPDATE`, чистка истории диалогов, удаление файлов в рабочей папке,
  удаление боевых воркфлоу/credentials. Сначала сказать, что именно и где будет удалено, и
  дождаться явного «да». Исключение — собственная техническая обвязка (временные SQL-раннеры,
  отладочные леса): убирать за собой можно свободно. При сомнении — считать данными и спросить.
- Credentials хранить только в n8n (не в коде, не в Sticky Notes).
- Webhook URL не публиковать.
- Для чувствительных персональных данных — локальная LLM (Ollama), не облако (152-ФЗ).
- Токены и секреты — через переменные окружения n8n, не хардкодить.
- API-ключи REST/MCP хранить в отдельном файле окружения вне репозитория (например
  `.n8n-api-key`, добавленный в `.gitignore`), а не в коде сценариев.
