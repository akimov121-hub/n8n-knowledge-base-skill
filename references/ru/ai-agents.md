### AI-Р3. Парсер ответа openAi-ноды v2.1 в JSON-режиме (text как dict, не строка)

- **Контекст:** при `options.textFormat.textOptions.type = "json_object"` нода
  `@n8n/n8n-nodes-langchain.openAi` v2.1 отдаёт `output[0].content[0].text` **как уже
  распарсенный dict**, а не строку JSON. Если Code-нода после неё пытается `JSON.parse(text)`
  — падает в fallback с пустыми полями, и весь pipeline даёт пустоту до самого конца.
- **Решение:** в Code-ноде поддерживать оба формата:

```js
const resp = $input.first().json;
const _t = resp.output?.[0]?.content?.[0]?.text;
let parsed = null;
if (_t && typeof _t === 'object') {
  parsed = _t;                              // новый путь: dict уже распарсен
} else if (typeof _t === 'string') {
  try { parsed = JSON.parse(_t); } catch(e) { parsed = null; }
}
if (!parsed || typeof parsed !== 'object') {
  parsed = { /* fallback с дефолтными полями */ };
}
```

Статус: ✅ Подтверждено в проде.

### AI-Р4. Инструмент-справочник для агента через Postgres full-text (RAG без векторов)

- **Контекст:** агенту нужен on-demand доступ к курируемому справочнику — цитаты, FAQ,
  регламенты, шаблоны писем, описания продуктов, нормы права. Полноценный векторный RAG не
  всегда доступен: на части shared-хостингов расширение `vector` (pgvector) **не установлено**
  (проверить: `SELECT count(*) FROM pg_available_extensions WHERE name='vector'`). Для корпуса
  в десятки–сотни записей семантика и не нужна.
- **Решение:** справочник = обычная Postgres-таблица + полнотекстовый поиск. Колонка
  `tsv tsvector` + GIN-индекс. Инструмент агента — нода `toolWorkflow` → суб-воркфлоу
  (`executeWorkflowTrigger` со входом `query` → Postgres `executeQuery`). Агент передаёт
  ключевые слова через `$fromAI('query', …)`.

```sql
CREATE TABLE ref (id SERIAL PRIMARY KEY, text_ru TEXT, text_en TEXT, theme TEXT, source TEXT, tsv tsvector);
UPDATE ref SET tsv = to_tsvector('russian', coalesce(text_ru,'')||' '||coalesce(theme,''))
                   || to_tsvector('english', coalesce(text_en,''));
CREATE INDEX ref_tsv_idx ON ref USING GIN(tsv);
```

Запрос в суб-воркфлоу (`queryReplacement = ={{ $json.query }}`; `$1` можно повторять):

```sql
SELECT text_ru, text_en, source FROM ref
WHERE tsv @@ plainto_tsquery('russian',$1) OR text_ru ILIKE '%'||$1||'%' OR theme ILIKE '%'||$1||'%'
ORDER BY ts_rank(tsv, plainto_tsquery('russian',$1)) DESC LIMIT 5;
```

- **Почему так:** корпус лежит в БД, агент достаёт топ-5 → на токены и скорость ответа размер
  базы **не влияет** (в отличие от «весь справочник в системный промт»). Масштабируется до
  сотен строк мгновенно.
- **Важно (качество):** инструмент только достаёт — за достоверность отвечает наполнение.
  Справочник выверять по авторитетному источнику. В промте обязать использовать дословно
  ТОЛЬКО то, что вернул инструмент, и не выдумывать, если поиск пуст.
- **Эволюция:** появится pgvector / Qdrant — переводится на семантику без смены интерфейса
  инструмента.

Статус: ✅ Подтверждено в проде.

### AI-Р5. Tool-хранилище агента с человекочитаемыми номерами (память, напоминания, списки)

- **Контекст:** инструмент агента (`toolWorkflow`) хранит личные записи пользователя (память,
  напоминания, todo) и показывает их номера в чате. Нужно: номера без дыр и переиспользование
  освободившихся, правка «на месте», минимум переспросов.
- **Паттерн (4 части):**
  1. **Номер = `id`, gap-fill.** `save/set` вставляет в наименьший свободный `id`
     (см. postgres.md PG-Р3). Показываемый номер = реальный PK, поэтому `delete`/`update`
     адресуются по нему напрямую.
  2. **Операция `update` (правка на месте).** Отдельный выход Route: вход `id` + новый полный
     `content`, пересчёт производных полей (для семантической памяти — заново эмбеддинг),
     `UPDATE … WHERE id=… RETURNING id`. НЕ delete+insert (иначе номер уезжает в конец).
  3. **Отображение — простой номер.** В Code-форматтере `'  '+r.id+'. '+text`, а не `[id N]`.
     В промпте — называть «номером», не «id».
  4. **Автономность по промпту.** Удаление/правку выполнять сразу, если запись определена
     однозначно. Переспрашивать ТОЛЬКО при неоднозначности. `id` в неизвестность — сперва
     `search`/`list`.
- **Деплой:** правка боевого `toolWorkflow` через PUT — сохранять node id, добавлять
  credentials в каждую ноду, после PUT проверять активность с ретраем (см. rest-api-deploy.md
  DEP-О6). SQL обкатывать на локальном Postgres до прода.

Статус: ✅ Подтверждено в проде.

### AI-Р6. Долговременная память о собеседнике «как у живого человека» (recall + capture)

- **Контекст:** бот должен помнить факты о собеседнике от беседы к беседе и сам вспоминать их
  без явной просьбы «вспомни» (пример: «еду в парк с собакой Рекс» → позже бот сам знает, кто
  такой Рекс). Отдельно от памяти диалога.
- **Паттерн (2 независимых механизма):**
  1. **Recall = «всё в контекст», без эмбеддингов и без поиска.** Перед агентом нода
     `Load Facts` (Postgres) тянет ВСЕ факты пользователя и склеивает в один блок:
     `SELECT COALESCE(string_agg('- ['||category||'] '||content, E'\n' ORDER BY category,id),'') AS facts_block ... WHERE telegram_id=...`.
     Блок вклеивается в System Message выражением
     `{{ $('Load Facts').first().json.facts_block }}`. Только так факт всплывает сам, без
     команды искать: семантический поиск тут НЕ работает — агент не догадается искать «Рекса».
     Эмбеддинги не нужны, пока фактов на пользователя десятки–сотни.
  2. **Capture = агент сам вызывает tool `save/update/delete`** (на базе AI-Р5, но без
     эмбеддингов). КЛЮЧЕВОЕ: одной мягкой инструкции в середине промпта НЕ хватает — модель
     фокусируется на ответе в роли и молча пропускает сохранение. Нужна **жёсткая директива у
     самого ВЕРХА** System Message: «системное действие — память, выполняется ВСЕГДА до
     ответа; если в сообщении есть новый/изменившийся факт о собеседнике — обязан вызвать
     memory.save/update, иначе ошибка». После этого вызывает стабильно.
- **Важный нюанс новизны:** агент меряет «новый ли факт» по **окну диалога**, а не по БД.
  Факт, уже сказанный в пределах окна, повторно НЕ сохранит. То, что обсудили ДО того как
  сохранение реально заработало, в базу само не доедет — занести руками. Чтобы доказать, что
  recall идёт из памяти, а не из окна, — очистить историю диалога.
- **telegram_id — не от модели.** В мультипользовательском боте `telegram_id` в tool
  прокидывается выражением `$('Normalize').first().json.telegram_id` (не `$fromAI`), иначе
  модель может перепутать пользователей.
- **Не реализовано (задел):** отдельный модуль извлечения фактов на mini-модели
  (детерминированный проход после ответа, пишет в обход агента). Самостоятельный приём для
  сценариев, где пропустить факт дорого: квалификация лидов, сбор анкетных данных из
  переписки, CRM-обогащение, поддержка с фиксацией деталей обращения. Детерминированный проход
  (всегда срабатывает, не зависит от настроения модели) надёжнее, чем «агент сам решает».

Статус: ✅ Подтверждено в проде (бот вспомнил факт после полной очистки истории диалога —
recall только из памяти фактов).

### AI-Р7. Tool-консультант сам пишет результат в БД (детерминированно), а агенту отдаёт исходный ответ

- **Контекст:** главный агент должен сохранять структурный результат подагента (программа,
  план, числа) в профиль. Если это делает сам агент через update-tool — шаг вероятностный и
  **молча пропускается** (пример: программа сгенерирована, но `program_json` остался NULL).
- **Решение:** запись делает **сам tool-воркфлоу консультанта** как побочный эффект, не завися
  от LLM. После ноды Agent: `Persist` (Code: парсит `{output}` агента, по `mode` строит
  `_sql`+`_params`) → `Save?` (IF `_save`) → `Save Field` (Postgres `executeQuery`,
  `query="={{ $json._sql }}"`, `queryReplacement="={{ $json._params }}"`) → `Return` (Code:
  `return [{ json: $('Agent').first().json }]` — отдаёт агенту ровно его ответ). Один Persist
  покрывает несколько режимов (PLAN→`nutrition_json`, CAFFEINE→`caffeine_mg/norm`).
  `telegram_id` — из входного `profile`.
- **Грабля (Code-нода):** в `runOnceForEachItem` возврат `[{ json: { …массив… } }]` падал
  `A 'json' property isn't an object [item 0]`. Лечение: **`runOnceForAllItems`** +
  `const out = $input.first().json;`.
- **Где НЕ так:** большие доки (program/nutrition_json) — пишет консультант, и из промта
  главного агента убрать «сохрани сам» (иначе двойная запись/гонка). Мелкие скаляры (вес,
  возраст) — по-прежнему агент через update-tool.

Статус: ✅ Подтверждено (изолированный тест PLAN+CAFFEINE, прод).

### AI-Р8. Проактивное напоминание должно ДОСЛОВНО повторять просьбу пользователя

- **Контекст:** агент по прямой просьбе ставит разовое напоминание (текст просьбы лежит в
  `note`), а отдельный крон-воркфлоу позже генерирует текст напоминания через короткий
  mini-LLM-промт и шлёт его (нода `Build Prompt`, ветка `kind='reminder'`).
- **Грабля:** generic-промт mini-LLM («напиши тёплое сообщение пользователю») скатывается в
  **дежурный вопрос** про самочувствие и НЕ упоминает саму просьбу. Пользователь не опознаёт
  сообщение как заказанное им напоминание — выглядит как случайный нудж. (Тул вызывался и
  срабатывал штатно — баг был не в «тул не вызвался», а в тексте генерации + опоздании до часа
  из-за ежечасного крона.)
- **Решение:** в промт ветки напоминания жёстко зашить: «Это напоминание по ЯВНОЙ просьбе.
  Начни со слов „Ты просил напомнить…" и ДОСЛОВНО укажи суть (`note`). НЕ превращай в дежурный
  вопрос. Пустая суть → короткое нейтральное напоминание». То есть `note` обязан попасть в
  текст вербатим, а не быть лишь «настроением» для свободной генерации.
- **Общий принцип:** когда отложенное сообщение порождается отдельным LLM-шагом, исходную
  интенцию пользователя нужно прокидывать в текст дословно — свободная генерация по «теме»
  теряет узнаваемость для адресата.

Статус: ✅ Подтверждено (короткий тест).

### AI-Р9. Дедупликация раздутого системного промта — единый канон вместо повторов (−25% токенов/оборот)

- **Контекст:** системный промт большого агента уходит в LLM на КАЖДОМ вызове — каждая лишняя
  строка оплачивается на каждом обороте. У зрелого промта со временем копятся дубли: один и тот
  же запрет/правило переписан в 3 разделах «для надёжности». Пример: промт раздулся до
  ~50000 симв.
- **Решение:** свести повторяющиеся блоки к **одному канону** + ссылки/дельты:
  - тройной запрет имён tools/полей → один канон (в «Жёстком контракте»), на который ссылаются
    остальные разделы;
  - три копии «когда звать подагента X» → один раздел маршрутизации;
  - три «перепиши ответ в свой голос» → один общий блок + короткие дельты по типам;
  - три «деградация при ошибке тула» → одна;
  - ~60 перечисленных имён для определения пола → правило + короткий список-пример.
  Результат: 49967 → 37613 симв (**−24,7%**) без изменения поведения и смысла.
- **Грабли/границы:** (1) дедуп — это рефакторинг промта, проверять поведенчески (прогон
  сценариев), а не только по диффу; (2) НЕ оставлять в теле промта changelog/«было-стало» —
  это снова токены на каждом обороте; историю держать в журнале версий. (3) Канон должен быть в
  разделе, который агент точно прочитает (верх/контракт), иначе ссылки «см. выше» рискуют.

Статус: ✅ Подтверждено (короткий тест).

### AI-Р10. Длинный структурированный вывод бота прятать в раскрывающуюся цитату Telegram (`<blockquote expandable>`) через сентинел-маркер + пост-нода

- **Контекст:** агент иногда отдаёт большой структурированный блок (программа тренировок, план
  питания, длинный список) — в чате это «простыня», которую неудобно листать. Telegram умеет
  схлопывать такой блок в раскрывающуюся цитату (`<blockquote expandable>…</blockquote>`), но
  тег работает **только при `parse_mode` HTML или MarkdownV2** и содержимое внутри должно быть
  валидно экранировано.
- **Решение (разделение ответственности модель ↔ детерминированная нода):**
  1. **Модель оборачивает блок простым сентинелом**, а не пишет HTML сама: в System Message —
     правило «полную программу/план оберни в `⟪PROGRAM⟫ … ⟪/PROGRAM⟫`, а перед маркером дай
     1–2 строки сути». LLM не заставляют генерировать корректный HTML (она бы напутала с
     экранированием) — только поставить дешёвый текстовый маркер.
  2. **Отдельная пост-нода перед отправкой** (`Clean Output`, Code) находит блок по сентинелу и
     конвертирует в `<blockquote expandable>`, **экранируя только содержимое блока** (`&`→`&amp;`,
     `<`→`&lt;`, `>`→`&gt;`) — остальной текст не трогает.
  3. **Обратная совместимость:** нет сентинела → текст уходит без изменений. Существующие
     ответы не ломаются.
- **Важные нюансы:**
  - `parse_mode` пайплайна должен уже быть HTML (см. telegram.md TG-Р2) — тег в plain-режиме
    придёт сырым текстом.
  - **Не резать сплиттером 4096 внутри блока** — разрыв `<blockquote>` посередине ломает
    разметку. Если блок может превысить лимит — резать по границам блока, не внутри.
  - Сентинел брать «экзотический» (`⟪ ⟫`), чтобы не столкнуться с обычным текстом
    пользователя/модели.
- **Общий приём:** любую «модель генерит → нода форматирует» задачу с хрупким целевым
  синтаксисом (HTML, MarkdownV2, JSON) строить так: модель ставит простой маркер,
  детерминированная нода превращает его в целевой синтаксис с правильным экранированием.
  Надёжнее, чем доверять экранирование LLM.

Статус: ✅ Подтверждено (рендерится в Telegram корректно).

### AI-Р11. Агент должен честно озвучивать грубость точности крон-доставки, а не обещать точное время

- **Контекст:** агент по просьбе ставит разовое напоминание, но доставляет его отдельный крон с
  грубой гранулярностью (**раз в час** — осознанный замысел, не «менеджер напоминаний»).
  Пользователь просит «напомни через 10 минут».
- **Грабля:** агент дружелюбно повторяет за пользователем — «Хорошо, через 10 минут напомню».
  Но крон сработает на ближайшем часовом тике → реально придёт в пределах часа. Обещание
  точного времени **вводит в заблуждение** (особенно на интервалах меньше шага крона), хотя сам
  механизм исправен.
- **Решение:** в промт зашить честность про точность: не обещать доставку до минуты и не
  повторять «через N минут», если N меньше шага крона; на короткий интервал — предупредить
  «сверяюсь примерно раз в час, ровно к этой минуте не выйду, напомню в пределах ближайшего
  часа» и всё равно поставить (или предложить привязать к конкретному времени, если нужна
  точность); на конкретное время/часы — подтверждать без «секунда в секунду». Частоту крона при
  этом НЕ менять.
- **Общий принцип:** когда исполнение асинхронно и грубо по времени (крон, очередь, батч),
  ожидание по точности задаёт ответ агента — формулировка должна соответствовать реальной
  гранулярности доставки, а не желаемой пользователем. Чинить ожиданием, а не обязательно
  частотой.

Статус: ✅ Принято к выкатке (правка на проде; финальная визуальная проверка — тестировщиком).
Связано с AI-Р8 (тот же крон).

### AI-Р12. Веб-чат поверх ТОГО ЖЕ агента — сквозная история Telegram↔веб через общий sessionKey=telegram_id

- **Контекст:** у Telegram-бота-агента появился второй канал (веб/Mini App-чат). Нужно, чтобы
  это был **один диалог**, продолжающийся в обоих каналах, а не два изолированных бота с
  раздельной памятью.
- **Решение:** новый канал собрать как агент с **тремя общими компонентами**: (1) **тот же
  системный промт** (читать из той же `prompts.<name>`), (2) **та же Postgres Chat Memory с тем
  же `sessionKey`** = `telegram_id` пользователя (а не chat_id веб-сессии!), окно то же, (3)
  **та же модель**. Тогда обе ветки пишут/читают одну таблицу `<bot>_chat_history` по одному
  ключу → история сквозная: ответил в Telegram — видно в вебе, и наоборот.
- **Изоляция без расшаривания нод:** сам веб-воркфлоу — **отдельный** (`<workflow_name>`), не
  трогает основной бот (`<workflow_name>` байт-идентичен). Общее — только данные (таблица
  памяти, строка промта, credential модели), не ноды. Это защищает основной бот от регрессий
  при правках веб-канала.
- **`chat/history` для UI — порядок.** Чтобы отдать фронту **последние N** реплик и при этом
  **по возрастанию** (старые сверху): `SELECT … ORDER BY id DESC LIMIT N`, затем **развернуть
  массив в Code**. `ASC LIMIT N` вернёт начало истории (не хвост); `DESC` без разворота — ленту
  задом наперёд. Tool-сообщения (`type='tool'` и ассистентские тех-строки) отфильтровать.
- **Граница (осознанная):** к веб-агенту можно НЕ подключать тулы основного бота
  (подагенты/проактив/напоминания) ради изоляции — тогда веб-чат это «чистый разговор» на общей
  памяти, а инструментальные сценарии остаются за Telegram. Tool-parity — отдельная задача.
- **Зеркалирование** второго канала в Telegram-диалог (чтобы веб-реплики появлялись и в чате с
  ботом) — см. telegram.md TG-Р16; вход веб-канала через Login Widget — telegram.md TG-Р14.

Статус: ✅ Подтверждено на проде (история по возрастанию; `chat/send` пишет оба сообщения в
общую память, ответ агента приходит).

### AI-Р13. Тул отложенного follow-up должен уметь СЕГОДНЯ: убрать жёсткий пол, прошедшее время → ближайший слот окна, иначе следующий день (зеркалить reminder-тул)

- **Контекст:** у агента есть инструмент «запланировать follow-up» (`schedule_followup`):
  аргумент `in_days` + час, запись в `proactive_queue`, доставку делает крон. Логически «давай
  вечером пообщаемся / попозже сегодня» — это follow-up на **сегодня**.
- **Грабля:** тул имел жёсткий пол `in_days = Math.max(1, …)` — структурно НЕ умел планировать
  на сегодня. Любая просьба «сегодня вечером» молча уезжала на завтра (`due_at` = завтра 19:00).
  Со стороны пользователя: «обещал пообщаться вечером — и не написал сегодня». Баг не в вызове
  тула (он срабатывал), а в нижней границе диапазона + в описании аргумента, которое не
  разрешало «сегодня».
- **Решение (три слоя, все обязательны):**
  1. **Убрать пол:** `in_days = Math.max(0, Math.min(30, Number(t.in_days)||0))` (0 = сегодня).
  2. **Вычисление `due_at` зеркалить с reminder-тулом, а не «тупой +N дней»:** если расчётное
     `due0 <= now()` (в таймзоне пользователя) — сдвиг на **ближайший целый час в окне доставки
     крона** (≤ верхней границы окна, напр. 20:00); если уже позже окна — на **следующий день**
     в запрошенный час. `in_days≥1` (будущее) — без изменений. Сделано CTE `adj` в SQL
     Insert-ноды по образцу reminder-тула.
  3. **Описание аргумента + промт обязаны явно разрешать «сегодня»:** текст
     инструмента/`$fromAI`-подсказка — «0 = сегодня (вечером/позже сегодня), 1 = завтра, 2–3 =
     через пару дней»; в промт агента — маршрутизация «сегодня вечером/попозже» → `in_days:0`
     (или `set_reminder` на конкретное время), «завтра/через пару дней» → `in_days≥1`. Без
     этого модель всё равно планирует на завтра, даже если бэкенд уже умеет сегодня.
- **Общий принцип:** допустимый диапазон планирующего тула должен включать «сейчас/сегодня», а
  вычисление времени доставки — учитывать, что запрошенный момент мог уже пройти (сдвиг на
  ближайший слот, не на завтра вслепую). И границы диапазона, и **описание аргумента, и промт**
  должны разрешать ближнюю границу — иначе обещание «вечером» структурно невыполнимо. Логику
  «прошедшее время → ближайший слот / следующий день» переиспользовать из reminder-тула, не
  изобретать заново.
- **Нюанс капа:** если у проактива есть суточный кап (напр. мягкий проактив 1/календ. день),
  same-day follow-up сработает, только если проактива сегодня ещё не было. Для гарантированной
  доставки на сегодня — связка с `set_reminder` (обходит окно/кап).

Статус: ✅ Подтверждено (тесты: in_days=0 утром → сегодня 19:00; in_days=0 поздно/ночью →
завтра; in_days≥1 как раньше). Зеркалит AI-Р8/AI-Р11 (тот же крон) и логику reminder-тула.

### AI-Р14. «Проактивный» тул-вызов: формулировка «сначала ответь словами, потом вызови» подавляет вызов — нужно «вызови в том же ходе, это фоновый тул» + пример + «при сомнении ставь»

- **Контекст:** агент-тулзовик (продукт-коуч) должен в подходящих случаях САМ, без просьбы
  пользователя, вызывать фоновый инструмент (`schedule_followup` — запланировать «как прошло»),
  а пользователю отдавать обычный текст.
- **Грабля 1 — порядок:** инструкция «Сначала ответь словами, ПОТОМ тихо вызови» не работает. У
  tools-агента финальный текст всегда идёт ПОСЛЕДНИМ (ReAct-цикл: думаю→тул→…→финальный ответ),
  «ответить раньше тула» физически нельзя, и такая формулировка делает вызов **опциональным** —
  модель выдаёт ответ и тул роняет. Симптом: на явный триггер («посмотрим, как пройдёт день»)
  тул не вызывается, хотя в промте описан как обязательный.
- **Грабля 2 — мягкость:** «вызывай, когда уместно… не злоупотребляй» модель читает как «по
  умолчанию не вызывай». Для проактивного (не по прямой просьбе) поведения этого мало.
- **Решение (формулировка промта):**
  1. **Убрать ложный порядок:** не «сначала ответь, потом вызови», а «**вызови в ТОМ ЖЕ ходе; это
     ФОНОВЫЙ инструмент — пользователь вызова не видит; порядок вызова и текста неважен, важно не
     забыть вызвать**».
  2. **Тул = обязанность, не опция** + список явных триггер-фраз дословно («посмотрим как пройдёт
     день», «как пойдёт», «дальше видно будет») + правило «**при сомнении — ставь**» (лучше лишний
     раз, чем промолчать).
  3. **Конкретный пример** вход→вызов:
     `«посмотрим, как пройдёт день» → schedule_followup(in_days:0, when:вечером, note:"…")`.
  4. Для **анти-дубля и снятия** дать агенту видимость уже запланированного: подгружать открытые
     записи `proactive_queue` в контекст каждого хода (нода `Load Pending`→в `packet`) + отдельный
     тул отмены (`cancel_followup`, UPDATE done=true по id). Тогда модель и не плодит дубли, и сама
     снимает касание, когда пользователь отчитался по теме.
- **Проверка:** до правки тул на явный триггер не вызывался; после — стабильно вызывается на
  постановку (`schedule_followup`) и на отмену по отчёту пользователя (`cancel_followup`),
  повторных вопросов от вечернего крон-тика не возникает.

Статус: ✅ Подтверждено (постановка и снятие проверены в проде).

### AI-Р15. Еженедельный глубокий разбор данных пользователя — выделенный промт + калибровка по объёму + строгий JSON под сворачивающийся UI

- **Задача:** не «пересказ метрик за период», а аналитический разбор — связи между
  показателями, причины, динамика, персональные рекомендации. Источник «фишки» продукта —
  функция «Итоги недели» у продукта-коуча.
- **Решение (паттерн):**
  1. **Отдельный промт** (строка в `prompts`, читается воркфлоу), а не основной агентский —
     наследует персону/голос/философию из главного промта, но добавляет МЕТОДОЛОГИЮ анализа:
     явные требования искать корреляции (X→след. день Y), главный рычаг, динамику + сравнение
     период-к-периоду, аномалии, скрытый риск, «тихую победу», и ОДНО ключевое неочевидное
     открытие с цифрами.
  2. **Богатый вход:** не только метрики дневника, но и **переписка** пользователя (history,
     фильтр `type<>'tool'`, последние N сообщений, чистка служебной шапки) — даёт «почему» за
     цифрами; + профиль/цель/факты + прошлый период для сравнения.
  3. **Калибровка по объёму данных:** передавать в промт число дней с данными
     (`days_with_data`) и тиринг: мало (≤1) — честный снимок без анализа + призыв заполнять; 2–3
     — лёгкий разбор, НЕ выдумывать корреляции/риски; ≥4 — полная глубина. Жёстко: «честность
     важнее объёма, пустые секции опускай». Иначе модель фабрикует связи на пустом месте.
  4. **Строгий JSON по схеме** (headline / key_insight{title,text} / sections{...} /
     correlations / hidden_risk / quiet_win / overall / recommendations[{what,why,how}]) —
     парсится в БД и рендерится сворачивающимися карточками. `key_insight.title` — короткий
     ЯРЛЫК (3–6 слов), иначе модель пишет туда целое предложение и «заголовок» раздувается.
  5. **Локализация в тексте:** явно требовать русские названия метрик (не латинские ключи
     mood/energy) — иначе разбор пестрит англ. ключами из входных данных.
- **Гейт генерации:** только при ≥2 непустых записей (иначе разбор не о чем), тумблер согласия,
  нет отчёта за этот период (UNIQUE + NOT EXISTS). Раз в неделю → модель не жалко (большая
  модель, большой промт).

Статус: ✅ Подтверждено (качество разбора на реальных данных, деградация на бедных данных).
Связано: AI-Р6 (память о собеседнике).

### AI-Р16. Жёсткий лимит длины: LLM не считает символы → запас в цели + детерминированный тримминг

- **Симптом:** просишь модель «итог ≤950 знаков», а она регулярно перелетает (1000–1100).
  Telegram-подпись ≤1024, у нас рабочий потолок 950 → пост не уходит / кнопка блокируется.
- **Причина:** LLM **не умеет точно считать символы** — «≤950» она воспринимает как «примерно
  столько», целясь ~в лимит и часто перебирая.
- **Решение (две меры):**
  1. **Запас в цели промпта:** просить меньше лимита — «целься в 820–880 знаков, СТРОГО ≤950,
     лучше короче, чем впритык». Модель приземляется под порог.
  2. **Детерминированный гарант после модели** (Code-нода), не доверяя счёту LLM: если результат
     > лимита — обрезать по **границе предложения**:

```js
let text=(p.post||'').trim();
if(text.length>950){const cut=text.slice(0,950);const m=cut.match(/[\s\S]*[.!?…](?=\s|$)/);text=(m?m[0]:cut).trim();}
```

     Гарантирует ≤950 без обрыва на полуслове (режется только хвостовое предложение, что с
     запасом в цели бывает редко).
- **Правило общее:** для ЛЮБОГО жёсткого числового ограничения, которое выдаёт LLM (длина,
  кол-во пунктов), не полагаться на сам промпт — добавлять детерминированную проверку/обрезку в
  коде. Промпт снижает частоту, код гарантирует.

Статус: ✅ Подтверждено.

### AI-Р17. Кап «N проактивных касаний в сутки» — счётчик+дата в профиле, а не один last_at; + разнос по времени

- **Контекст:** проактивные сообщения (продукт-коуч) надо ограничивать по числу в сутки.
  Изначально было 1/день через `last_proactive_at::date < сегодня` — но это жёстко 1, и не
  масштабируется на «до 2».
- **Грабля:** один timestamp `last_proactive_at` не хранит счётчик — на нём «2 в сутки» не
  сделать.
- **Решение:** добавить в профиль `proactive_day date` + `proactive_count int`. Гейт выборки:
  `(proactive_day IS DISTINCT FROM сегодня OR COALESCE(proactive_count,0) < N)`. При отправке
  (не-reminder) апдейт: `proactive_count = CASE WHEN proactive_day=сегодня THEN count+1 ELSE 1
  END, proactive_day=сегодня`. Дату считать в таймзоне пользователя
  (`(now() AT TIME ZONE timezone)::date`).
- **Разнос по времени (важно):** при веере (обработка всех кандидатов за тик) без интервала два
  касания могут уйти в соседние часовые тики подряд. Добавить
  `AND last_proactive_at < now() - interval '4 hours'` — тогда N касаний разнесены, а не идут
  пачкой. Дедуп по telegram_id в Build Prompt гарантирует ≤1 сообщение пользователю за тик.
- **Явные напоминания (reminder) не капать** — отдельная ветка, не трогает счётчик.

Статус: ✅ Подтверждено (миграция, гейт исполняется).

### AI-Р18. Монетизационный гейт перед агентом: fail-open, за дедупом, абсолютные счётчики из гейта

- **Задача:** триал/лимиты тарифов для LLM-бота (триал N сообщ/M дней, месячные лимиты, гейты

### AI-Р21. Фазовый блок промта по условию (триал/сегмент) без поломки префикс-кэша

### AI-Р22. Платная генерация контента в вебхуке: гейт → LLM-JSON → gpt-image → INSERT (квота не сгорает при сбое)

- **Цена вопроса:** mini-LLM ≈ копейки + генератор изображений medium 1024² ≈ $0.04–0.05 на

### AI-Р23. Vision для еды: mini-модель не хуже топовой и дешевле; распознавание через HTTP + max_completion_tokens

- **Тарифный гейт распознавания = как в основном боте** (одни тарифы допускают, другие нет);

### AI-Р24. Гигиена долговременной памяти: TTL + еженедельная авторевизия с code-guard

- **Симптом:** память-агент копит «факты навсегда» без различия постоянное/временное —
  устаревшие обещания и разовые события засоряют контекст и попадают не в ту категорию.
- **Решение (3 слоя):**
  1. **Промт записи:** строгие категории (семья = только постоянное + питомцы; обещания с датой

     существующее → update, не дубль).

     обстоятельств); ночной cleanup удаляет протухшие.
  3. **Еженедельная ревизия** (cron вс + ручной вебхук): mini смотрит факты каждого пользователя
     с датами → JSON `{delete[],update[]}`. **КРИТИЧНО — предохранитель в коде строже промта:**
     применяющий Code-узел разрешает delete только для категорий «события»/«контекст», update —
     только с реально изменённым текстом (не no-op); семья/ценности/привычки/работа
     неприкосновенны на уровне SQL. Dry-run поймал попытку mini удалить полезную привычку — без
     code-guard ревизия сама разрушала бы память.
- **Тест перед боем:** прогонять ревизию в dry-run (только вернуть план, не применять) на
  реальных данных нескольких пользователей — увидеть, что LLM хочет удалить.

### AI-Р30. Действие в мини-аппе, продолжаемое агентом в чате (seed в chat-memory)

### AI-Р27. Проверка изменения промта на СИНТЕТИЧЕСКОМ профиле + безопасная дедупликация промта

### AI-Р28. Устойчивый парс LLM-JSON в tool-ноде записи: ремонт скобок + честный `throw` (не тихий `{}`)

- **Симптом:** пользователь надиктовал/сфоткал еду, бот ответил «Записал питание за сегодня…»,
  но в Mini App «Питание по плану» — пустые кнопки 1–5 (не пилюля «% нормы»), вкладка Питание
  пуста. Исполнение бота — `success`.
- **Причина:** узел записи парсил аргумент `metrics` от агента как
  `try{JSON.parse(s)}catch{metrics={}}`. Модель вернула `food_log` с битым JSON — массив открыт
  `[`, закрыт `}` вместо `]` (пропущена `]`). `JSON.parse` бросил → catch **молча обнулил ВСЕ
  метрики того вызова** → запись не выполнилась, шёл только SELECT recent → tool вернул success
  → агент решил, что записал, и **соврал пользователю**. Тихая потеря данных под статусом
  success.
- **Решение (два слоя):**
  1. **Ремонт JSON перед сдачей** — `repairJson()`: посимвольный проход со стеком скобок
     (учитывает строки/эскейпы), чинит несовпадающие/недостающие `]`/`}` (закрыватель не той
     скобки → заменить на правильный для верхушки стека; в конце добить незакрытые), срезает
     ```-обёртку. Пропущенная `]` в `food_log` чинится.
  2. **Не врать при провале** — если и после ремонта не парсится: `console.log(raw)` + `throw`
     (агент получает ошибку → честно «не смог записать, повтори»), а НЕ тихий `metrics={}`.
     Валидный путь — байт-в-байт прежний; пустой `metrics` (только чтение) — без throw.
- **Проверка:** тест на реальном битом JSON пользователя (несколько блюд чинятся, запись есть),
  на валидном (не сломан), на мусоре (throw), на пустом (только SELECT).
- **Общий принцип:** любой аргумент-JSON от LLM в tool-ноду парсить с ремонтом + честной ошибкой
  при провале; НИКОГДА не подменять на `{}`/`[]` под видом успеха — иначе агент рапортует успех,
  а данных нет. Родственные: AI-О4 (устойчивость парсера к мусору), AI-Р7 (детерминированная
  запись мимо LLM), AI-Р22 (throw до записи — квота цела).

Статус: ✅ Подтверждено.

### AI-Р29. Проактивная воронка по дням: детерминированный отбор + свободный текст от LLM

- **Задача:** вести пользователя по платному триалу (или онбордингу) касаниями, а не надеяться,
  что модель сама запланирует follow-up. Инцидент: ведение по триалу «остановилось» — агент
  написал один раз, юзер ответил, нового follow-up агент не поставил, а порог «молчит ≥3 дня»
  ещё не наступил → тишина в самую конверсионную неделю. Системной воронки не было вообще:
  ведение держалось на решении модели.
- **Паттерн (что кому решает):**
  - **День касания выбирает SQL, а не LLM.** Ветка в отборе кандидатов: `plan='trial'`, день =
    `extract(day from now() - trial_started_at)`, `dn IN (1,3,5,6)`. Детерминированно,
    воспроизводимо, видно в БД.
  - **Задача дня — в промпте, текст — от модели.** У каждого дня своя цель (первый шаг →
    вовлечь в нетронутый раздел → показать динамику → мягко про подписку). Шаблонные рассылки
    читаются как спам; цель + контекст профиля/дневника дают живой текст.
  - **Защита от повтора — лог в той же очереди:** после отправки
    `INSERT INTO proactive_queue (kind='trial', note='day:N', done=true)`, а в отборе
    `NOT EXISTS(... kind='trial' AND note='day:N')`. Не нужна отдельная таблица, идемпотентность
    при любом числе тиков шедулера.
  - **Приоритет веток через `prio` + `UNION ALL`:** явное напоминание пользователя (0) → воронка
    (1) → follow-up (2) → молчание (3), плюс дедуп «одно сообщение в тик на юзера».
  - **Порог молчания зависит от стадии:** на триале 1 день, на платном 3 дня —
    `CASE WHEN p.plan='trial' THEN interval '1 day' ELSE interval '3 days' END`. Одинаковый
    порог либо теряет триальщика, либо надоедает подписчику.
- **Обязательное окно:** отправка только в дневные часы по `timezone` пользователя + не чаще
  раза в N часов, иначе воронка накладывается на обычные касания.

Статус: 🟡 Черновик (внедрено, отбор проверен вхолостую; подтверждение по первым живым
касаниям — на будущее).

## ⚠️ Ошибки

### AI-О1. `pairedItem` рвётся на ноде `@n8n/n8n-nodes-langchain.openAi` v2.1

- **Симптом:** в выражении после openAi v2.1 пишешь `$('Имя_ноды').item.json.поле` —
  возвращается `undefined`. Нода ниже получает пустые параметры (в Telegram sendPhoto это
  даёт `Bad Request: there is no photo in the request`), хотя предок реально вернул значение.
- **Причина:** нода openAi v2.1 не пробрасывает pairedItem-метаданные. `.item` использует
  pairing для определения «какой item родителя породил текущий», и без них падает в undefined.
  Особенно больно в цепочках вида `imgBB → openAi → sendPhoto`, где url берётся через
  cross-node ref.
- **Лечение:** во ВСЕХ cross-node выражениях, где между источником и потребителем стоит хотя
  бы одна openAi v2.1 — использовать `.first()` вместо `.item`:
  - ❌ `$('Загрузить в imgBB').item.json.data.url`
  - ✅ `$('Загрузить в imgBB').first().json.data.url`
- **Профилактика:** по умолчанию писать `.first()` всегда в cross-node refs — это безопасно
  во всех случаях, а `.item` использовать только когда явно нужна привязка к pairing.

### AI-О2. Инструмент-агента (`toolWorkflow`) молча возвращает «недоступен», если суб-воркфлоу деактивирован

- **Симптом:** агент в чате отвечает «инструмент сейчас недоступен». При этом execution
  основного бота — статус **success** (не error), так что в логах сходу не видно. В runData
  проблемной tool-ноды лежит:
  `{"response": "There was an error: \"Workflow is not active and cannot be executed.\""}`.
  Сами tool-воркфлоу при этом **не имеют отдельных executions** (вызов инлайн в родителе).
- **Причина:** суб-воркфлоу-инструмент (триггер `executeWorkflowTrigger`) переведён в
  `active=false`. При вызове через AI Agent такой воркфлоу отдаёт ошибку строкой в `response`,
  агент трактует её как «инструмент недоступен». Родительский execution остаётся success —
  ошибка не всплывает в Error Workflow.
- **Лечение:** реактивировать tool-воркфлоу: `POST /api/v1/workflows/{id}/activate`. Для
  `executeWorkflowTrigger` активация безопасна — сам по себе он не запускается.
- **Диагностика:** не доверять статусу `success` родителя. Открыть execution основного бота с
  `includeData=true`, в `runData` проверить `response` у каждой tool-ноды на подстроку
  `There was an error`. Параллельно `GET /api/v1/workflows/{id}` по каждому инструменту →
  `active`.
- **Профилактика:** держать tool-воркфлоу всегда active. **Важно:** после
  `POST /api/v1/workflows` нового tool-воркфлоу он создаётся неактивным — сразу `/activate`.

### AI-О3. Postgres Chat Memory падает `Got unexpected type: constructor` на ручной INSERT в историю

- **Симптом:** после того как сторонний воркфлоу (проактивный рассыльщик) вписал сообщение в
  таблицу истории чата, **КАЖДОЕ следующее сообщение пользователя роняет основной бот** — нода
  Memory бросает `Got unexpected type: constructor` (видно в runData узла памяти и в Error
  Workflow). До первого ручного INSERT бот работал.
- **Причина:** запись сделана в формате langchain **Serializable `toJSON()`** —
  `{"lc":1,"type":"constructor","id":["langchain_core","messages","AIMessage"],"kwargs":{"content":…}}`.
  А загрузчик Postgres Chat Memory n8n (`mapStoredMessageToChatMessage`) понимает только
  **StoredMessage**: `{"type":"ai"|"human"|"tool","content":"…",…}` (content на ВЕРХНЕМ уровне,
  без `kwargs`). На `type:"constructor"` бросает исключение, и весь круг агента падает.
- **Лечение:** ручной INSERT в таблицу истории — только StoredMessage:
  `{"type":"ai","content":<text>,"tool_calls":[],"additional_kwargs":{},"response_metadata":{},"invalid_tool_calls":[]}`.
  Уже записанные битые строки чинить UPDATE:
  `SET message=jsonb_build_object('type','ai','content',message->'kwargs'->>'content','tool_calls','[]'::jsonb,'additional_kwargs',COALESCE(message->'kwargs'->'additional_kwargs','{}'::jsonb),'response_metadata',COALESCE(message->'kwargs'->'response_metadata','{}'::jsonb),'invalid_tool_calls','[]'::jsonb) WHERE message->>'type'='constructor'`
  (контент сохраняется).
- **Профилактика:** (1) когда вручную пишешь строку, которую читает ДРУГАЯ нода (chat memory,
  очередь) — сначала прочитать реальную строку, записанную самим потребителем, и повторить её
  схему 1:1, не угадывать. (2) E2E-тест проактива покрывает ПОЛНЫЙ цикл с потребителем:
  отправить сообщение И затем ответить юзером, убедившись, что память грузится; «сообщение
  ушло» — недостаточно. (3) не копировать унаследованный код (формат из прошлой версии) без
  сверки — унаследованное ≠ корректное.

Статус: ⚠️ Подтверждено на проде, исправлено (формат записи + починка битых строк UPDATE'ом).

### AI-О4. Recovery-парсер лика тул-вызовов дублирует запись при повторном маркере

- **Контекст:** gpt-5.4 иногда «сливает» вызов инструмента текстом — печатает
  `to=functions.<tool>` + JSON-аргументы прямо в ответ вместо нормального tool-call (нередко с
  мусорными токенами). Защита: нода-recovery (Code) сканит `output` агента на `to=functions.X`,
  парсит JSON и САМА применяет запись (INSERT/UPDATE) — сам тул при этом не исполнился.
- **Симптом:** одно действие записалось **дважды** из одного круга (два идентичных напоминания
  в `proactive_queue`).
- **Причина:** в слитом тексте маркер `to=functions.X` встретился НЕСКОЛЬКО раз, а JSON-блок
  аргументов — один. Парсер на каждый маркер берёт ближайший следующий `{…}` → оба маркера
  схватили ОДИН и тот же JSON → два одинаковых INSERT.
- **Лечение:** дедупить одинаковые стейтменты в одном круге recovery:
  `const uniq=[...new Set(stmts)]; if(!uniq.length) return []; return [{json:{sql:uniq.join('\n')}}]`.
  Безопасно: разные легитимные записи отличаются текстом и сохраняются, идемпотентные повторы
  схлопываются.
- **Профилактика:** любой парсер недетерминированного вывода LLM (лик тул-вызова, свободный
  текст) проектировать устойчивым к повторам/мусору — дедуп результатов или привязка JSON к
  конкретному маркеру по позиции.

Статус: ⚠️ Подтверждено на проде, исправлено (дедуп в Parse Writes).

### AI-О5. Follow-up уехал на завтра из-за жёсткого пола `in_days≥1` — обещание «вечером» не выполнилось

- **Контекст:** агент договорился с пользователем «давай вечером пообщаемся», вызвал тул

### AI-О7. Reasoning-модели ломают парсер ответа: текст НЕ в `output[0]`, а в item `type='message'`

- **Симптом:** приложение «зависло» на генерации. Исполнение n8n — **success за 17–21с**, но
  узел парсинга вернул `{header:"",post:""}` → в БД сохранился **пустой пост** → фронт поллит
  результат до таймаута. Ошибки нигде нет: и n8n, и модель отработали «успешно».
- **Причина (ТРИГГЕР — смена модели на reasoning, не «само сломалось»):** узел openAi v2.1
  (Responses API) на reasoning-моделях возвращает `output` **списком из 2+ элементов**:
  `output[0].type='reasoning'`, текст — в `output[1].type='message'` →
  `content[0].type='output_text'`. Парсер брал жёстко `resp.output?.[0]?.content?.[0]?.text` →
  `undefined` → пустой объект → пустые поля.
  **Как выяснили:** соседний узел на mini-модели (`reasoning_tokens: 0`) отработал нормально, а
  узел на reasoning-модели (`reasoning_tokens: 355`) — сломался. То есть ломались ровно те ноды,
  что перевели на reasoning-модель (правка была сделана **вручную в UI**, мимо генератора
  конфигурации → он ещё показывал прежнюю модель = дрейф).
  **Маркер:** `usage.output_tokens_details.reasoning_tokens > 0` → модель в reasoning-режиме →
  конверт ответа другой.
- **Решение — искать message-item, а не индекс:**

```js
var _o = resp.output || [];
var _m = _o.find(x => x && x.type === 'message') || _o[_o.length-1] || {};
var _c = _m.content || [];
var _i = _c.find(x => x && (x.type === 'output_text' || x.text !== undefined)) || _c[0] || {};
var _t = _i.text;   // строка или уже объект (json_mode)
```

  Работает и на моделях без reasoning (там message = единственный элемент). Применять и в
  Code-нодах, и в Set-выражениях.
- **Масштаб (важно):** паттерн копируется по всем AI-веткам — задело более десятка узлов в
  нескольких боевых воркфлоу (препроцессор, редактор, соавтор, правки текста,
  арт-директор/image_prompt, генерация подписи, парсер времени). **При такой поломке проверять
  ВСЕ парсеры разом** (`grep 'output?.[0]'` по экспорту), а не только тот, где заметили.
- **Профилактика (первопричина «тихого зависания»):** пустой результат от AI = **сбой**, а не
  «ещё считается». Фронт/потребитель обязан отличать: если бэкенд ответил, но текст пустой —
  сразу ошибка пользователю, без поллинга до таймаута.
- **Диагностика:** «зависло» + исполнения success по 20с → смотреть не таймауты, а **что реально
  сохранил парсер**; затем структуру `output` живого ответа (`executions/{id}?includeData=true`).
- **Правило на будущее:** смена поколения/типа модели = **смена формы ответа**, а не только
  качества. После перевода на reasoning-модель — перепроверить ВСЕ парсеры этой ветки
  (`grep 'output?.[0]'` по экспорту) и прогнать по одному живому вызову на каждую AI-ветку.
  Правка модели в UI мимо генератора конфигурации создаёт дрейф. Родственная запись — AI-О6
  (смена поколения роняет узлы устаревшими параметрами).

Статус: ✅ Исправлено и проверено вживую.

### AI-О8. Агент говорит о СЕБЕ в роде пользователя

- **Симптом:** бот-персона мужского пола пишет женщине о своих действиях в женском роде: «Имя,
  **записала** питание за сегодня» (должно — «записал»). Поймано тестировщицей.
- **Причина:** в промте род персонажа нигде не задан явно, а поле профиля описано как «`gender`

- **Проверка без вторжения в чужой диалог:** временный воркфлоу с тем же системным промтом +
  СИНТЕТИЧЕСКИЙ профиль-блок женщины + один LLM-вызов на прод-модели. Не минтить токен реального
  пользователя и не писать в его живую переписку (это выдача себя за другого).
- **Урок:** любые ролевые/грамматические свойства персоны (род, возраст, «я») задавать явно — то,

### AI-О9. Бот-echo теряет уведомление владельцу при недоставке ответа юзеру

- **Симптом:** бот техподдержки (чистый Webhook+HTTP, паттерн Mirror Echo) — исполнения падают
  на узле `Send Reply` с `Bad Request: chat not found`. Причём падает ВЕСЬ сценарий, и
  уведомление владельцу (`Notify Owner`), которое стоит ПОСЛЕ отправки ответа юзеру, **не
  срабатывает — баг-репорт теряется**.
- **Причина:** 1) «chat not found» при валидном приватном `chat_id` = юзер ещё не нажал `/start`
  у бота (или заблокировал/удалён) — обычная для прода ситуация, бот не может инициировать
  диалог. 2) У Telegram-HTTP-узлов нет `onError` → любая недоставка роняет всю цепочку;
  уведомление владельцу, завязанное на успех предыдущего узла, гибнет вместе с ней.
- **Решение:**
  - На ВСЕ внешние отправки (`sendMessage` юзеру, стартовое сообщение) —
    `onError: continueRegularOutput`, чтобы недоставка не роняла сценарий.
  - **Ветку уведомления владельцу нельзя ставить в зависимость от успеха ответа юзеру.** Либо
    `onError=continue` на `Send Reply` (тогда цепочка идёт дальше к Notify), либо развести их
    параллельно от общего узла. Notify читает данные из узла-парсера (`$('Parse Reply')`), не из
    отправки — тогда доходит всегда.
  - Первопричину «chat not found» лечит только сам юзер: нажать `/start`. Но уведомление о баге
    должно доходить и без этого.

Статус: ⚠️ Поймано в live-исполнениях и исправлено.

### AI-О20. Промт внутри `jsonBody` HTTP-ноды: перебор с экранированием роняет ноду `invalid syntax`

- **Симптом:** заменили системный промт в HTTP-ноде (вызов модели напрямую, `jsonBody` =
  `={{ JSON.stringify({...}) }}`) — воркфлоу сохранился без ошибок, API отдал 200, но при первом
  же запуске нода падает с `invalid syntax`, бот молчит для пользователей.
- **Причина:** промт лежит внутри JS-строки в двойных кавычках. В дампе через API кавычки видны
  как `\"`, и легко «на автомате» заэкранировать их ещё раз (`\\"`), получив битое выражение.
  Ошибка не ловится ни валидацией n8n, ни сохранением — только реальным исполнением.
- **Лечение:** экранировать РОВНО один раз: `"` → `\"`, перенос строки → `\n`. Плюс заранее
  проверять, что в тексте промта нет `{{` / `}}` — n8n примет их за своё выражение.
- **Обязательный шаг:** после правки промта — **живой прогон**, а не только проверка `GET`
  (текст в дампе может выглядеть правильно при сломанном выражении). Для вебхук-ботов с
  секретом: POST на вебхук с нужным заголовком и проверка `status='success'` в
  `execution_entity`, иначе правка «прошла», а бот мёртв.
- **Страховка:** перед правкой сохранить исходный `jsonBody` в файл — откат тогда занимает один
  PUT.

### AI-О10. Агент врёт про «вчера»: даты в данных есть, но модель их неверно вычитает

- **Симптом:** агент называет ТОЧНЫЕ цифры (калории, сон, настроение сходятся с БД до единицы),
  но привязывает их не к тому дню: «после вчерашнего недосыпа» — хотя вчера сон был 7 ч, а
  недосып случился позавчера. Пользователь ловит на факте, которого не было, и перестаёт
  доверять всему разбору, включая верные числа.
- **Причина:** в контекст приходит текущее время (`[YYYY-MM-DD HH:mm]` в шапке сообщения) и
  записи дневника с полем `date` в ISO-формате. Разницу «сегодня минус дата записи» модель
  считает САМА — и на этом шаге ошибается, особенно когда в выборке несколько похожих дней
  подряд. Данные при этом не галлюцинация: берётся реальный день, просто соседний.
- **Лечение — промтом, без правки пайплайна:** правило «прежде чем сказать
  „вчера/позавчера/на выходных“ — вычти дату записи из текущей и проверь слово; если день важен
  для смысла (недосып, срыв, рекорд) — называй дату или день недели: „в субботу, 25.07“; если за
  нужный день записей нет — так и скажи, не подставляй соседний».
- **Почему именно так:** требование называть дату делает ошибку видимой обеим сторонам и
  заставляет модель выполнить вычитание явно, а не «на глаз». Подтверждено: после правки все
  цифры и дни в ответе совпали с БД, недосып переименован из «вчерашнего» в «недавний»
  (корректно).
- **Альтернатива, если промт не помогает:** подавать в контекст готовые ярлыки
  (`позавчера (сб, 25.07)`) вместо голых дат — тогда вычислять нечего. Дороже (правка сборки
  контекста во всех местах), поэтому начинать стоит с промта.
- **Как ловить:** выгрузить ответы агента и грепнуть относительные слова
  (`вчера|позавчера|на днях`), затем сверить упомянутые числа с таблицей за соответствующие
  даты. Ошибка на день видна сразу.

Статус: ⚠️ Грабля → ✅ лечение подтверждено.

### AI-О11. Агент-мужчина пишет о себе в женском роде, подстраиваясь под собеседницу

- **Симптом:** в переписке с женщиной агент вдруг говорит о СВОИХ действиях в женском роде:
  «Имя, записала питание за сегодня» (вместо «записал»). Персонаж ломается, выглядит как сбой
  движка.
- **Причина:** русский род глагола модель согласует по ближайшему одушевлённому контексту — им
  оказывается собеседница, чьё имя и пол упомянуты рядом. Один случай на ~150 ответов, поэтому в
  ручном тестировании почти не ловится.
- **Лечение:** явное правило в промте: «независимо от пола собеседника, о своих действиях говори
  в мужском роде: записал, посчитал, обновил, понял; не подстраивай свой род под род
  собеседницы. К пользователю обращайся в ЕГО роде (поле gender профиля)».
- **Как ловить:** грепом по ответам агента искать женские формы первого лица
  (`записала|посчитала|обновила|поняла|отметила`) — для агента-мужчины любое совпадение является
  дефектом.

Статус: ⚠️ Грабля (правило добавлено).

### AI-О12. Агент не чувствует, что разговор прервался на ночь: в истории диалога нет времени

- **Симптом:** вечером обсудили планы «на завтра», человек пишет утром — а агент продолжает
  вчерашнюю реплику: «на сегодня разгрузка почти закончена, отложи работу до утра», «завтра
  решишь следующий баг». Хотя это утро УЖЕ то самое завтра. Со стороны выглядит как
  невнимательность: человек живёт в новом дне, а собеседник дописывает вчерашний вечер.
- **Причина:** Postgres Chat Memory хранит только роль и текст (`StoredMessage`), БЕЗ отметок
  времени. Для модели вся история выглядит как непрерывный разговор «только что». Текущее время
  приходит лишь в шапке нового сообщения — и само по себе оно проблему не решает, потому что
  модель не сопоставляет его с историей, если её об этом не попросить.
- **Лечение промтом:** правило «в истории диалога нет времени; единственный ориентир — метка в
  шапке текущего сообщения; между ним и прошлой репликой могли пройти часы, ночь или дни. Если
  наступил новый день (по дате или по времени суток) — планы „на завтра“ из прошлого разговора
  стали планами на сегодня; не предлагай отложить до утра, когда утро уже наступило».
- **Альтернатива (дороже):** писать время в сам текст сохраняемых сообщений или подмешивать
  `[дата время]` в историю при сборке контекста — тогда модели нечего домысливать. Требует правки
  пайплайна памяти, поэтому начинать стоит с промта.
- **Родственная грабля:** AI-О10 — там модель неверно вычитает даты дневника; здесь — не замечает
  разрыв между репликами. Обе про то, что у LLM нет собственного чувства времени: всё, что не
  подано явно, она достраивает.

Статус: ⚠️ Грабля (правило добавлено).

### AI-О13. Дорогая LLM-функция без счётчика = дыра в экономике

- **Симптом:** распознавание еды по фото было разрешено на триале и на премиуме, но **лимит
  проверялся только у премиума** (100/мес). Триальный пользователь мог за 7 дней настрелять
  сколько угодно кадров.
- **Цена вопроса:** vision-запрос ≈ $0.0023 (картинка 1024 px, detail high, ~1215 входных
  токенов). Прибыль с триала +$0.29 — то есть 60 фото за пробную неделю обнуляли её полностью,
  100 уводили в минус.
- **Вторая половина проблемы:** соседний маршрут «оценить КБЖУ по названию» вообще не имел
  гейта — ни тарифа, ни счётчика. При утечке токена сессии его можно дёргать в цикле.
- **Решение:** (1) лимит на каждом тарифе, а не только на верхнем:
  `LIMITS = { trial:5, basic:10, advanced:30, premium:100, tester:null, super:null }`,
  незнакомый план трактуется по самому строгому; (2) на дешёвый, но открытый маршрут — суточный
  технический потолок (30/сут), не показываемый в интерфейсе: живому человеку хватает с запасом,
  автоперебор упирается сразу.
- **Правило:** заводя LLM-функцию, сразу отвечай на два вопроса — сколько стоит один вызов и что
  мешает вызвать его тысячу раз. Если ответ на второй «ничего» — счётчик обязателен, даже когда
  вызов дешёвый.
- **Отдельно:** сверяй модель в воркфлоу с моделью в расчёте экономики — расхождение может
  завысить/занизить расчётную себестоимость в разы.

Статус: ✅ Исправлено (оба API-воркфлоу).

### AI-О14. Модель кладёт в структурное поле не то, что оно значит

- **Симптом:** пользователь попросил поправить конкретную тренировку. Субагент-тренер вернул
  режим `PROGRAM`, где в поле `exercises` (список упражнений) оказались фразы-указания:
  «Оставить 1 км лёгкого бега», «Убрать 3 круга приседаний». Название дня получилось «Перед
  бегом», а числовое поле длительности не соответствовало расписанному.
- **Причина:** промпт описывал, ЧТО класть в поле, но не запрещал класть туда другое и не
  требовал сверять числовое поле с содержанием. Плюс не был разведён сценарий «собрать
  программу» и «поправить одну тренировку» — модель упаковала правки в структуру программы.
- **Решение в промпте:** (1) явный запрет на глаголы-указания в списке с примерами
  неверно/верно; (2) формат названия дня — группа мышц или день сплита, не момент времени; (3)
  требование сложить разминку + работу + заминку и сверить с числом длительности перед выдачей;
  (4) отдельный раздел «когда НЕ нужен режим PROGRAM» — правки разовой тренировки отдаются
  текстом в диалог.
- **Общее правило:** для каждого структурного поля в промпте полезно давать пару «неверно /
  верно» на реальном промахе и объяснять, ЧТО пользователь увидит в интерфейсе. Абстрактное
  «список упражнений» модель трактует шире, чем нужно.

Статус: ✅ Применено, ждёт проверки на живых диалогах.

### AI-О15. Модель считает сумму по-своему: итог отдавать серверу, модели оставлять слагаемые

- **Симптом:** метрика «Жидкость» у пользователя занижена и «то работает, то нет». Разбор
  исполнений: агент прислал разбивку `{вода:3000, кофе:400, другое:250}` и итог `water: 3000`, а
  позже снова разбивку `{вода:3000, кофе:600}` и опять итог `3000`. То есть разбивку он ведёт
  верно, а в итог кладёт только воду.
- **Причина:** в промте было написано «`water` — ЛЮБАЯ выпитая жидкость», но у слова `water`
  есть собственное бытовое значение, и модель раз за разом ложится на него, а не на определение
  из инструкции. Плюс её просили выполнить арифметику (сложить разбивку) — операцию, где ошибка
  не видна ни в логах, ни в статусе `success`.
- **Отдельно:** иногда напиток не попадал вообще — на «два дрип-кофе плюс маленький энергетик»
  ушло `{caffeine:320}` без единого миллилитра, при этом в ответе агент бодро отчитался, что
  отметил оба напитка. Отчёт модели о своих действиях — не доказательство, что действие
  выполнено.
- **Решение:** забрать у модели итог целиком. Она ведёт только разбивку по типам (`liquid_mix`),
  сумму считает SQL в узле записи. Ручной ввод из приложения не затирается: он живёт как разница
  между сохранённым итогом и суммой разбивки.
- **Грабля миграции:** старые дни имеют итог и не имеют разбивки. Слепое «итог = ручное + сумма»
  задваивает воду. Развели тремя ветками: разбивка уже есть → ручное = итог − разбивка; разбивки
  нет, но модель прислала ключ «вода» → ручное = 0 (её разбивка и есть весь день); разбивки нет
  и воды в присланном нет → ручное = весь старый итог, напитки прибавляются сверху.
- **Как проверять такие правки:** сгенерировать SQL локально, прогнать на боевой БД внутри
  `BEGIN … ROLLBACK` разовым воркфлоу на несколько сценариев (старый день, старый день без воды
  в присылке, тап в приложении, чистый день, ручная добавка), сверить с ожидаемыми числами,
  удалить воркфлоу. Дешевле, чем ловить регресс через неделю по жалобе.
- **Правило:** модели — факты и слагаемые, коду — арифметика и итоги. Каждое число, которое
  модель складывает сама, рано или поздно разойдётся с реальностью молча.

Статус: ⚠️ ошибка подтверждена на исполнениях; решение применено, SQL проверен на 5 сценариях в
откатанной транзакции, 🟡 ждёт подтверждения на живых диалогах.

### AI-О16. «последние N сообщений» ≠ «за период»: окно контекста режется по времени, а не по счётчику

- **Симптом 1 (недельный отчёт).** У пользователя, который почти не пишет в чат, отчёт за неделю
  оказался собран из событий трёхнедельной давности — отказ от курения и срыв модель поставила
  на другой день недели. У активного пользователя тот же отчёт выглядел безупречно.
- **Причина.** Переписка бралась как `ORDER BY id DESC LIMIT 50` — без границы по датам. У
  активного это ровно текущая неделя, у молчуна — месяц с лишним. Хуже того, код сборки промта
  регуляркой **вырезал метку даты** из каждого сообщения, а блок подписывался «ПЕРЕПИСКА ЗА
  НЕДЕЛЮ». Модель сделала ровно то, что ей сказали.
- **Отдельная деталь:** большая часть сообщений в окне была неотвеченными проактивными пингами
  самого бота («давно не списывались»). Для молчуна канал переписки почти не несёт сигнала, но
  вытесняет всё остальное.
- **Симптом 2 (бот поддержки).** Бот восемь раз подряд задал одни и те же три диагностических
  вопроса, хотя человек на все ответил. В модель уходило ТОЛЬКО текущее сообщение — истории не
  было вовсе.
- **Решение.** Окно всегда ограничивать периодом: в отчёте — неделей отчёта, в поддержке — 12
  сообщений и не старше 3 суток. Метки времени НЕ вырезать: без них модель не отличит вторник от
  прошлого месяца. Если за период сообщений нет — так и написать модели («в чат не писал, строй
  по дневнику»), а не подсовывать чужой период под правильным заголовком.
- **Как ловить.** Считать по каждому пользователю: сколько сообщений всего и сколько попадает в
  окно. Расхождение вида «87 всего / 0 за неделю» — это и есть диагноз.
- **Правило.** Заголовок блока в промте — это обещание. Если написано «за неделю», данные
  обязаны быть за неделю; иначе модель добросовестно врёт по вашей же инструкции.

Статус: ⚠️ обе ошибки подтверждены на исполнениях; решения применены и проверены (поддержка —
живым прогоном, отчёт — подсчётом окна по нескольким пользователям).

### AI-О17. Бот отвечает «вижу фото», не имея зрения

- **Симптом:** пользователь присылает скриншот, бот пишет «Спасибо, вижу фото 🙏» и тут же
  спрашивает «что именно на экране — белый экран, загрузка или ошибка?». Так несколько
  скриншотов подряд.
- **Причина:** в модель уходила строка `[приложено фото]` — и всё. Картинка не скачивалась и не
  разбиралась вовсе. Формулировка «вижу фото» жила в промте как вежливость и превратилась в
  прямую ложь.
- **Решение:** контур зрения (getFile → скачать → data URL → vision-запрос → описание в текст
  сообщения) плюс правило в промте: опирайся на разбор, не спрашивай «что на экране»; если
  разобрать не удалось — честно скажи и НЕ пиши, что видишь.
- **Побочно найдено:** ответы содержали `**жирный**`, а `parse_mode` у `sendMessage` не задан —
  звёздочки уходили пользователю как есть. Чистим в парсере ответа и запрещаем markdown в промте.
- **Правило.** Вежливые формулировки в промте не должны утверждать способность, которой у бота
  нет. «Вижу», «посмотрел», «проверил» — либо правда, либо из промта вон.

Статус: ✅ проверено живым прогоном на реальном скриншоте — бот распознал экран входа и повёл по
входу вместо списка вопросов.

### AI-О18. Ремонт битого JSON доставил отчёт, но выпотрошенным: чинить надо причину

- **Симптом:** двум пользователям из пяти недельный разбор пришёл почти пустым — заголовок есть,
  содержания нет. Исполнение при этом `success`, доставка прошла.
- **Причина в два слоя.** Первый: у ноды не был задан потолок вывода, и длинный разбор
  обрывался на середине. Второй, коварнее: наша же автопочинка добивала недостающие скобки — и
  складывала `sections`, `correlations`, `recommendations` ВНУТРЬ `key_insight`. JSON становился
  валидным, но структура — чужой. Приложение читает эти поля на верхнем уровне и показывало
  пустоту.
- **Решение:** `maxTokens` задан явно (8000) плюс режим
  `textFormat: {textOptions:{type:'json_object'}}` — валидность гарантирует сам API. Ремонт
  остаётся страховкой, а не рабочим механизмом.
- **Ловушка при включении json_object:** нода отдаёт уже РАЗОБРАННЫЙ объект, а не строку.
  Код-сборщик, который делал `JSON.parse`, получал `[object Object]` и молча выбрасывал все
  отчёты. Поймано сухим прогоном до выката; сборщик научен принимать обе формы.
- **Правило:** автопочинка данных обязана быть заметной. Если она сработала — это инцидент, а не
  норма: логировать и лечить причину. «Валидный JSON» и «правильная структура» — разные вещи,
  проверять надо вторую.
- **Как проверять:** сухой прогон на РЕАЛЬНОМ контексте тех, у кого сломалось (контекст берётся
  из старого исполнения), сквозь всю цепочку до сборщика, без отправки в Telegram.

Статус: ✅ Проверено сквозным прогоном на контекстах обоих пострадавших пользователей, структура
верхнего уровня правильная, вложенности нет.

### AI-Р31 — Модель дороже для клиентского агента, дешевле для внутреннего
- **Наблюдение:** в паре ботов на одной базе клиентский продавец работает на DeepSeek
  (диалог с покупателем, важна убедительность и персона), а внутренний бот-аналитик для
  сотрудников магазина — на Qwen (Alibaba Cloud). Роли разведены: продавец пишет ЖИВЫМ
  клиентам и должен звучать хорошо, аналитик отвечает СОТРУДНИКАМ на фактические вопросы
  по данным (продажи, товары) — точность важнее стиля, дешевизна оправдана.
- **Правило для будущих клиентских ботов:** не одна модель на весь проект — сортировать
  агентов по цене ошибки и требованиям к слогу, клиентский/продающий контур получает
  более сильную модель, внутренний/справочный — более дешёвую.
- **Источник:** сравнение двух учебных воркфлоу курса (продающий агент vs внутренний
  аналитик продаж).
- **Статус:** 🟡 Черновик (референс курса).

### AI-Р32 — Анализ качества звонков: двойная транскрипция + реформат в Code перед LLM
- **Задача:** оценить работу оператора по записи разговора — с разделением реплик по
  говорящим, а не сплошным текстом.
- **Паттерн:**
  - **Два независимых пути транскрипции под разные источники входа.** Голосовое в
    Telegram (короткое, один канал) → нативная OpenAI-нода `transcribe`. Файл через веб-форму
    (более длинный звонок, нужна диаризация) → AssemblyAI: `Upload` → `Create a transcription`
    → `Wait` → `Get a transcription` (poll). Не единый маршрут «на всё» — выбор инструмента
    под формат входа.
  - **Между транскрипцией и LLM — Code-нода, которая схлопывает массив `utterances` в
    читаемый диалог** (`Спикер N:\nтекст`, через `\n\n`). Отдавать агенту сырой JSON с
    таймкодами не нужно — модель работает с текстом диалога, разметка не несёт для неё
    пользы, только шум.
  - **Промт задаёт роль явно через контекст, а не входной параметр**: «определи, кто из
    спикеров оператор (здоровается от лица компании, задаёт вопросы, решает проблему),
    оцени только его работу» — вместо того чтобы просить оператора и клиента помечать себя
    заранее.
  - **Строгий формат ответа без пояснений** (Оператор/Тема/Оценка N/10/Слова-паразиты/Плюс/
    Минус) — при передаче результата дальше в Telegram-сообщение не нужен парсинг, весь
    ответ — уже готовый текст карточки.
  - **Явная инструкция не додумывать**: «диаризатор иногда ошибается — анализируй только то,
    что прозвучало чётко» и «суди только по сказанному, не додумывай и не смягчай» —
    страховка от типовой слабости LLM достраивать недостающее (см. [[AI-агенты#AI-О10]],
    [[AI-агенты#AI-О12]] — тот же класс проблемы, там про даты и разрывы во времени).
  - **Потенциал применения:** прямое пересечение с задачами контроля качества звонков у
    клиентов на фрилансе (тот же класс задачи уже встречался в презентациях под другие
    проекты).
- **Источник:** учебный воркфлоу анализа звонков курса.
- **Статус:** 🟡 Черновик (референс курса, не прогонялось).

### AI-Р33 — Контент конкурента → структурированный разбор с доказательной базой → генерация с трассируемостью приёма
- **Задача:** автоматически разобрать выгрузку постов конкурента, вытащить рабочие приёмы
  контента и сгенерировать новые посты на их основе — не копируя, а используя структуру.
- **Паттерн:**
  - **Двухфазный структурированный вывод**: `Structured Output Parser` заставляет модель
    СНАЧАЛА заполнить `analysis.patterns[]` (имя приёма, формат, угол подачи, тип хука,
    `evidence` — сколько постов подтверждают приём, `reliable` — булев самооценённый флаг
    доверия), и только ПОТОМ сгенерировать `posts[]`, где у каждого поста есть поле
    `pattern`, ссылающееся на конкретный приём из первой фазы. Готовый пост нельзя
    сгенерировать «из воздуха» — он обязан указывать, на каком именно найденном приёме
    основан. Это и есть трассируемость: если приём слабый (`evidence` мало,
    `reliable: false`), видно, на чём стоит сгенерированный пост.
  - **`analysis.reach_note`** — отдельное поле «менялись ли охваты внутри периода и как это
    учтено» — модель обязана явно отчитаться, не исказила ли анализ разница в охватах
    старых/новых постов, а не молча усреднить несравнимые цифры.
  - **`analysis.excluded`** — число отброшенных постов, тоже явное поле, не спрятанное —
    виден масштаб исходных данных, из которых сделан вывод.
  - **Источник постов конкурента — VK API `wall.get`** с `owner_id`, начинающимся с минуса
    (отрицательный ID = группа/паблик, не пользователь) — рабочий способ забрать
    паблик-контент конкурента без парсинга HTML.
  - **Картинка генерируется по промту, привязанному к посту**: `image_prompt` (английский,
    со сценой) + `image_text` (дословная надпись на картинке) — разделены, потому что модели
    генерации изображений плохо держат длинный русский текст в кадре, но хорошо — сцену по
    английскому описанию.
- **Риск, который сам паттерн не решает:** «разобрать приёмы конкурента и написать по ним
  посты» — это близко к копированию, а не вдохновению; для клиентской работы такое стоит
  явно проговаривать с заказчиком (репутационный, не только юридический вопрос).
- **Источник:** учебный воркфлоу «контент-фабрика: анализ + визуал + текст» курса.
- **Статус:** 🟡 Черновик (референс курса, не прогонялось).

### AI-Р34 — ИИ поверх детерминированных цифр: SQL находит, модель объясняет; строгая JSON-схема через HTTP Request

- **Паттерн:** поиск паттернов — правила в SQL (счётчики, промежутки, сравнение периодов),
  тексты карточек — шаблоны с подстановкой цифр. Модель получает уже посчитанные факты
  (цифры, распределения, последние события, «память объекта» — прошлые карточки с
  комментариями людей и их 👍/👎) и отдаёт гипотезу, что проверить, вопрос человеку.
  Статусы меняет только человек; сбой модели не блокирует детерминированную часть.
- **Как вызывать:** HTTP Request `POST https://api.openai.com/v1/chat/completions` с
  `authentication: predefinedCredentialType`, `nodeCredentialType: openAiApi` (учётка
  продукта — правило «по ключу на продукт»); тело — `response_format: { type: 'json_schema',
  json_schema: { strict: true, schema: {…, additionalProperties: false, required: [все
  поля]} } }`. Для gpt-5.x — `reasoning_effort: 'low'` и `max_completion_tokens`, **без
  `temperature`** (отвергается). Модель — из списка `/v1/models` на ключе корпоративного
  клиента (доступны до gpt-5.6; взята `gpt-5.4-mini`).
- **Разбор:** JSON с ремонтом (обёртка/код-блок), провал — `throw` в общий канал ошибок, не
  тихий пропуск (см. AI-О13). Нода разбора в режиме **Run Once for Each Item**, иначе после
  IF `$('Промт').item` теряет пару.
- **Промт:** правила «опирайся только на приведённые цифры и называй их», «низкая
  уверенность при нехватке данных», «без внутренних кодов» + абзац справки о предметной
  области. Для пересказа руководителю — отдельный промт «без внутренних терминов, цифры
  только там, где меняют вывод».
- **Источник:** воркфлоу корпоративного клиента — детектор гипотез по проблеме и недельный
  пересказ мониторинга, 10.09.2026.
- **Статус:** ✅ Подтверждено — раздел «Проблемы» проверен на телефоне 10.09.2026 (7 карточек).
