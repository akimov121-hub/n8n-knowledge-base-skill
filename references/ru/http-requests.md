# HTTP-запросы к внешним API

Вызовы сторонних HTTP-API из n8n напрямую (не через готовые интеграционные ноды): HTTP Request нода, multipart/form-data, работа с бинарём, ограничения Code-ноды (нет авторизованных хелперов, нет Web API), таймауты на длинные синхронные ответы и асинхронный паттерн опроса.

---

## ✅ Решения

### HTTP-Р1 — ~~Comma-separated `inputDataFieldName` для N файлов~~ ОПРОВЕРГНУТО
**Статус:** ⚠️ Опровергнуто (реальное решение — HTTP-Р2)
**Симптом / контекст:** нужно отправить на внешний API multipart с несколькими файлами под одним именем поля (`image[]`), число файлов заранее неизвестно (1–4).
**Что считалось решением:** `parameterType: formBinaryData`, `inputDataFieldName: "={{ $json.refKeys }}"` со списком имён через запятую («n8n сам разбивает comma-separated список»).
**Почему это неверно:** n8n comma-separated список НЕ разбирает. В исходниках (`HttpRequestV3.node.ts`, проверено на 2.26.8 и master) `assertBinaryData(itemIndex, cur.inputDataFieldName)` получает строку как **одно имя поля** → с двумя+ референсами нода падает `The item has no binary field 'ref0,ref1'`. Изначальная запись была подтверждена, судя по всему, только одно-референсными прогонами (`refKeys="ref0"` — без запятой), где схема вырождается в обычное одиночное поле.
**Источник:** сервис генерации изображений; инцидент (первый реальный вызов с 2 референсами).

### HTTP-Р2 — Отправка N файлов (динамическое число) в multipart: Switch + K копий HTTP-ноды
**Статус:** ✅ Подтверждено (мульти-реф и текстовый режим проверены прогонами; результат, собранный этой схемой, утверждён заказчиком)
**Симптом / контекст:** тот же, что в HTTP-Р1: multipart с 1–4 файлами под одним именем поля `image[]`, число файлов динамическое. Ограничения платформы (проверено по исходникам n8n 2.26.8):
- comma-separated в `inputDataFieldName` не разбирается (см. HTTP-Р1);
- `formBinaryData` с пустым/несуществующим именем поля при `typeVersion ≥ 4.2` роняет ноду `Cannot read properties of undefined (reading 'value')` (`prepareRequestBody`: `entry[key].value` при пропущенном параметре) — трюк «пустое имя = пропустить параметр» не работает;
- собрать multipart-Buffer вручную и отдать как raw-binary нельзя — см. HTTP-О2 (`source.on is not a function`): legacy-адаптер ядра при заголовке `multipart/form-data` пересоздаёт тело через spread объекта.
**Решение (работает):**
1. **Code-нода** декодирует файлы в бинарные свойства `ref0…refN-1` (`prepareBinaryData`) и отдаёт `refCount` в json.
2. **Switch-нода** по `{{ $json.refCount }}` (1/2/3/4) ветвит на…
3. …**K копий HTTP Request ноды** (`contentType: multipart-form-data`): в копии для K файлов — ровно K статических параметров `formBinaryData` с `name: "image[]"` и `inputDataFieldName: ref0…refK-1`. Дубли имени `image[]` допустимы — путь FormData делает `append` на каждый параметр отдельно. Все копии сходятся в одну ноду-декодер результата.
4. Авторизация в каждой копии: `authentication: predefinedCredentialType`, `nodeCredentialType: openAiApi` + явные `credentials` при PUT (см. rest-api-deploy.md).
**Пример:** сервис генерации изображений, ветка референсов: Switch «Сколько референсов?» → `OpenAI edits 1/2/3/4 реф` → «PNG из base64».
**Побочное:** gpt-image `/edits` отдаёт `b64_json` → декодер-Code-нода перед Respond (как раньше).
**Источник:** починка сервиса генерации изображений (инцидент: первый вызов с 2 референсами уронил воркфлоу).

### HTTP-Р3 — Асинхронный вебхук (job_id + опрос) для операций дольше 30 c
**Статус:** ✅ Подтверждено (`1024x1536`+`high` → PNG 1.2 МБ за 90 c из-под клиентской сети, где синхронный режим падал 100% раз)
**Задача:** отдать клиенту результат операции, которая идёт 60–150 c, при жёстком лимите ~30 c на длину HTTP-ответа (см. HTTP-О5). Поднять лимит нельзя — он вне вашей инфраструктуры.
**Решение — не держать соединение:** вместо одного длинного запроса два коротких (каждый ~1 c).
```
Webhook → IF «Роутер» (body.action == 'get')
  ├─да─→ SELECT job → Switch по status
  │        done    → Code(base64→binary) → Respond binary
  │        error   → Respond JSON {status:'error'}
  │        (fallback) → Respond JSON {status:'pending'}
  └─нет→ IF «есть prompt?» → INSERT job (pending) RETURNING job_id
           → IF «async?» ─да→ Respond 202 {job_id} ─┐  (выполнение ИДЁТ ДАЛЬШЕ)
                          └нет──────────────────────┤
                                                    ↓
                          [долгая работа] → Code(binary→base64) → IF «async?»
                                              да  → UPDATE job SET status='done', result_b64
                                              нет → Respond binary (старое поведение)
```
**Ключевые моменты:**
- нода `Respond to Webhook` **не завершает** воркфлоу — после неё выполнение продолжается, на этом и держится «ответить сразу, доделать потом»;
- после `Respond`/`INSERT` в `$json` уже другие данные → все выражения долгой ветки перепривязать на исходный запрос: `$('Webhook').item.json.body.*`;
- хранилище задач — обычная таблица (`job_id text PK, status, result_b64 text, …`), результат кладём base64-текстом; автоочистка старых записей CTE-запросом при INSERT: `WITH del AS (DELETE FROM t WHERE created_at < now() - interval '1 day' RETURNING 1) INSERT …`;
- флаг `async` в теле сохраняет обратную совместимость (без него — старый синхронный путь);
- параметры в SQL — через `queryReplacement` массивом-выражением (см. postgres.md PG-Р5).
**Пример:** сервис генерации изображений (`<workflow_id>`), таблица `img_jobs`.
**Источник:** переделка сервиса генерации изображений.

## ⚠️ Ошибки

### HTTP-О1 — Code-нода не может делать авторизованный HTTP-запрос
**Статус:** ⚠️ Ошибка (ограничение платформы)
**Симптом:** в Code-ноде `this.helpers.httpRequestWithAuthentication(...)` падает `The function "helpers.httpRequestWithAuthentication" is not supported in the Code Node`; `requestWithAuthentication` вовсе отсутствует. В `Object.keys(this.helpers)` они формально видны, но заблокированы в песочнице.
**Причина:** песочница Code-ноды запрещает авторизованные HTTP-хелперы (нельзя вытащить креды). Доступен только **неавторизованный** `this.helpers.httpRequest` / `request`.
**Решение:** любой вызов внешнего API, требующий креды n8n, делать **отдельной HTTP Request нодой** с `authentication: predefinedCredentialType` + `nodeCredentialType`. Секрет остаётся в n8n и не утекает в экспорт workflow.json. В Code-ноде — только сборка/разбор данных.
**Источник:** сервис генерации изображений (ветка референсов).

### HTTP-О2 — Готовый multipart-буфер в HTTP-ноду как raw-binary → `source.on is not a function`
**Статус:** ⚠️ Ошибка
**Симптом:** собрал multipart/form-data тело Buffer'ом в Code-ноде, отдал в HTTP Request ноду через `contentType: binaryData` (raw-бинарь) — нода падает `source.on is not a function`.
**Причина:** режим отправки бинаря ждёт stream-подобный источник, а не in-memory Buffer.
**Решение:** не собирать multipart вручную. Использовать **нативный multipart** HTTP-ноды (см. HTTP-Р2).
**Источник:** сервис генерации изображений.

### HTTP-О3 — Web API (`URLSearchParams` и пр.) недоступны в Code-ноде — сборка query/form только руками
**Статус:** ⚠️ Ошибка (ограничение платформы) + ✅ решение подтверждено (оплата прошла живьём)
**Симптом:** Code-нода падает `URLSearchParams is not defined (ReferenceError)`. Коварство: узел писался «на глаз» и падал у ВСЕХ вызовов, но снаружи это выглядело как «Некорректный ответ сервера» у клиента (вебхук с responseNode при падении узла отдаёт не-JSON), а обходные тесты (сборка URL в python) маскировали баг — живой E2E впервые нажали только через несколько дней.
**Причина:** песочница Code-ноды n8n не даёт браузерных Web API: `URLSearchParams`, `fetch`, `TextEncoder`… (тот же класс, что запрет `require('crypto')` — см. telegram.md TG-О10). Доступны только чистый JS + `encodeURIComponent`/`Buffer`.
**Решение:** query-string и form-urlencoded собирать руками:
```js
const pairs=[['MerchantLogin',ML],['OutSum',amount],['InvId',String(inv)]];
const qs=pairs.map(p=>encodeURIComponent(p[0])+'='+encodeURIComponent(p[1])).join('&');
```
Отличие от `URLSearchParams`: пробел кодируется `%20`, а не `+` — семантически эквивалентно, парсеры принимают оба.
**Профилактика:** (1) любой новый Code-узел прогонять живым вызовом до «готово» — «нода написана» ≠ «нода исполнялась»; (2) при «Некорректный ответ сервера»/не-JSON от вебхука первым делом смотреть executions воркфлоу (`status=error`, `resultData.error.message`), а не сеть/DPI; (3) grep `URLSearchParams|fetch\(|TextEncoder` по всем воркфлоу при подозрении — обычно находится единичный узел.
**Источник:** `<workflow_name>` продукта-коуч, ссылка на оплату Robokassa, инцидент «у нас ничего не работает»; несколько исполнений подряд падали с ошибкой.

### HTTP-О4 — Robokassa: Receipt в подпись идёт БЕЗ URL-кодирования (документация ошибается)
**Статус:** ✅ Подтверждено (боевой код отдаёт ссылку, форма принимает: ошибок нет, `isRecurring: true`, позиция в чеке есть)
**Симптом:** добавили номенклатуру чека (`Receipt`) в запрос на оплату — платёжная форма стала возвращать `error.code = 29`, поле `isRecurring` сбрасывалось в `false`, состав чека приходил пустым. Без `Receipt` тот же запрос принимался.
**Что говорит документация** (docs.robokassa.ru/ru/fiscalization): «Значение включается в подпись: `MerchantLogin:OutSum:InvId:Receipt:Пароль#1`. Перед добавлением в строку для подписи значение Receipt нужно URL-кодировать.»
**Что на самом деле:** боевая форма принимает подпись, посчитанную по **исходному JSON без кодирования**. С `encodeURIComponent` — код 29. Проверено перебором пяти вариантов (кодированная/некодированная подпись, `tax: none` и `vat0`, сумма числом и строкой, с `Recurring` и без) — расходился ровно один признак.
**Рабочая формула:** `md5(MerchantLogin : OutSum : InvId : <JSON Receipt как есть> : Пароль#1 : Shp_… по алфавиту)`. В самом запросе `Receipt` кодируется обычным образом при сборке query.
**Зачем вообще Receipt:** без него чек **не формируется вовсе** (нарушение 54-ФЗ), и часть способов оплаты не показывается на форме. В ответе формы это видно как `"receipt":{"items":[]}`.
**Как проверять без денег:** собрать ссылку на `/Merchant/Index.aspx` и запросить её curl'ом — платёжная форма отдаёт JSON состояния, где видно `error`, `isRecurring` и состав чека. Счёт создаётся, но списания не происходит.
**Состав для самозанятого (Робочеки СМЗ):** `{"items":[{"name":"…","quantity":1,"sum":<сумма>,"payment_method":"full_payment","payment_object":"service","tax":"none"}]}`. Поле `sno` не передаём — берётся из личного кабинета.
**Источник:** продукт-коуч, `<workflow_name>` (оплата) + `<workflow_name>` (рекуррентные платежи).

### HTTP-О5 — Долгий синхронный ответ вебхука рвётся на ~30 c ВНЕ сервера
**Статус:** ⚠️ Ошибка (сеть, вне инфраструктуры инстанса) + ✅ решение см. HTTP-Р3
**Симптом:** запрос к вебхуку, ответ на который готовится дольше ~30 c, стабильно падает `curl exit 56` / `Recv failure: Connection reset by peer` на 29–30 c. При этом воркфлоу в n8n **успешно завершается** за 60–120 c и отдаёт валидный результат (видно в executions). Тот же корень — обрывы **SSH** на длинных командах (`Connection reset by peer`, `timeout during banner exchange`).
**Ложная гипотеза (стоила времени):** «короткий read/response timeout прокси после переезда сервера». Неверно — прокси не виноват.
**Как проверять правильно (дёшево, без трат на платные API):** временный вебхук-пробник `Webhook → Code(await setTimeout(delay)) → Respond` и замер с трёх точек:
```
снаружи   45 c → ❌ обрыв 30.2 c        снаружи 25 c → ✅ 200
с сервера 45 c → ✅ 200 (n8n напрямую)  с сервера 45 c → ✅ 200 (через прокси)
```
Если **с сервера** проходит, а снаружи рвётся — виноват узел на маршруте (провайдер/DPI/NAT/VPN), а не прокси. Конфиги сервера трогать НЕ нужно.
**Профилактика:** TCP keepalive (`curl --keepalive-time`) НЕ помогает — режется по прикладному уровню. Для SSH помогает keepalive прикладного уровня:
```
Host <хост>
    ServerAliveInterval 15
    ServerAliveCountMax 10
```
**Источник:** сервис генерации изображений, инцидент (после переезда n8n на `<server_ip>`); проявилось на `1024x1536`+`medium/high`.
