# Отладка и sandbox

Отладка воркфлоу, sandbox-верстаки, экономия на дорогих сценариях.

---

## ✅ Решения

### DBG-Р1. Sandbox-верстак для дорогих сценариев

- **Контекст:** сценарий сжигает токены (LLM + веб-поиск + image-генерация) на каждом
  прогоне, а сломалась последняя миля (Telegram, HTTP-уведомление, запись в БД/Notion,
  формирование документа). Полный прогон ради проверки фикса — дорого.
- **Критерии завести sandbox:**
  - один полный прогон заметно дорог в токенах;
  - сломавшаяся часть — **выходная** нода (последняя миля);
  - ожидается серия итераций фикса (больше одной правки).
- **Структура:**

```
Webhook (POST /webhook/<имя>-test) → Set (данные как из реальной цепочки) → копия проблемной ноды
```

  Set формирует item ровно той структуры, которую видит проблемная нода в проде (подсмотреть
  в Output предыдущей ноды на реальном execution). Проблемная нода — точная копия с теми же
  `credentials`, `parameters`, `additionalFields`.
- **Правила хранения:** sandbox живёт в отдельной подпапке (`sandbox/<имя>/`) с собственным
  описанием и `workflow.json`. Дефолтные данные воспроизводят реальный упавший кейс. Параметры
  тестируемой ноды идентичны проду (`parse_mode`, `appendAttribution`, `binaryData`, заголовки
  HTTP) — иначе sandbox даст ложный «зелёный».
- **Правила публикации:** sandbox **не удалять после фикса** — живёт как инструмент для
  регрессий. После каждой сессии тестов **обязательно деактивировать**
  (`POST /api/v1/workflows/{id}/deactivate`); перед следующей — активировать обратно
  (`POST /api/v1/workflows/{id}/activate`). Активный публичный webhook без необходимости —
  лишний риск утечки URL.
- **Алгоритм по триггеру «проверь в песочнице»:** найти подходящий sandbox (или завести новый)
  → активировать → прогнать тесты curl-ом → деактивировать → применить фикс в проде.

Пример (curl читает домен и ключ из вынесенного файла окружения):

```bash
source ./.n8n-api-key   # экспортит N8N_API_KEY и N8N_BASE_URL

# активировать
curl -X POST -H "X-N8N-API-KEY: $N8N_API_KEY" \
  "$N8N_BASE_URL/api/v1/workflows/<sandbox_id>/activate"

# тест
curl -X POST "$N8N_BASE_URL/webhook/<sandbox-path>" \
  -H "Content-Type: application/json" \
  -d '{"text":"любой тест"}'

# деактивировать (обязательно после)
curl -X POST -H "X-N8N-API-KEY: $N8N_API_KEY" \
  "$N8N_BASE_URL/api/v1/workflows/<sandbox_id>/deactivate"
```

Статус: ✅ Подтверждено в проде.

### DBG-Р2. Порядок отладки упавшей ноды

1. Открыть Execution Log, найти упавшую ноду.
2. Посмотреть **Input** и **Output** этой ноды.
3. Проверить маппинг полей (expressions).
4. **Pin Data** — воспроизвести без реального триггера.
5. **Partial Execution** — запустить с проблемной ноды.

Доп. практики: Sticky Note с ожидаемыми данными; `console.log()` в Code Node (видно в логах);
тест на реальных данных через Pin Data перед продом.

### DBG-Р3. Песочница Code-ноды: нет URLSearchParams/TextEncoder/crypto.subtle — валидация initData чистым JS

- **Симптом:** Code-нода падает `ReferenceError: URLSearchParams is not defined` (а также нет `TextEncoder`, `crypto.subtle`). Веб-глобалы в песочнице n8n обрезаны; `Buffer` — есть.
- **Контекст:** валидация Telegram `initData` для Mini App = двойной HMAC-SHA256 (`secret=HMAC("WebAppData", bot_token)` сырыми байтами → `HMAC(secret, data_check_string)`).
- **Решение:**
  1. Парсить query вручную: `split('&')` + `decodeURIComponent` (без URLSearchParams).
  2. HMAC: пробовать `require('crypto')` (часто заблокирован `NODE_FUNCTION_ALLOW_BUILTIN`), фолбэк — **встроенный чистый JS SHA-256/HMAC** (на `Uint8Array`+`Buffer`). Алгоритм SHA-256 сверять портом на Python против `hashlib` (эмулировать JS-битовые операции `>>>`, `|0`, `~x` — совпало на всех векторах).
  3. Токен бота Code-нода из credential **не читает** → хранить в служебной таблице (`<config_table>`) или env, подгружать Postgres-нодой перед auth.
  4. `crypto.subtle` (Web Crypto) тоже отсутствует в этой песочнице — не рассчитывать.
- **Статус:** ✅ Подтверждено (фронт авторизуется в проде).

### DBG-Р4. Проверка сценария с расписанием в боевом рантайме: вебхук-дублёр «Прислать сейчас»

- **Приём:** ко второму входу цепочки добавить Webhook (GET, случайный путь вроде
  `agenda-now-<hex>`), ведущий в ту же первую рабочую ноду. `curl` по нему даёт
  production-исполнение (`mode: webhook`): Error Workflow срабатывает (на ручном Execute —
  нет), результат виден в Executions, расписание не трогается. Удобно и для итераций формата
  сообщения с владельцем: «пришли ещё раз» = один curl.
- **Одноразовый вариант:** через PUT переставить cron на «сейчас + 3 мин», дождаться, вернуть
  исходный файл тем же PUT (снимок перед PUT — обязателен). Годится, когда дублёр насовсем не
  нужен.
- **Риск:** чужой, узнавший путь, может спамить владельцу. Путь держать только в приватном
  описании; в сценарии дублёр шлёт тому же получателю, что и расписание, чужому ничего не
  уходит.
- **Статус:** ✅ Подтверждено.

### DBG-Р5. Имитация апдейтов Telegram Trigger без реального Telegram: секрет вебхука = `<workflowId>_<nodeId>`

- **Задача:** проверить бота (сообщения, callback-кнопки, `/start` с payload) от имени другого
  пользователя, не имея второго аккаунта и не дёргая людей.
- **Решение:** Telegram Trigger регистрирует вебхук с `secret_token` и отвечает 403 на POST без
  заголовка `X-Telegram-Bot-Api-Secret-Token`. Секрет считается в
  `GenericFunctions.getSecretToken`: `${workflow.id}_${node.id}` с вычищенными символами вне
  `[A-Za-z0-9_-]`. Id ноды берётся из `GET /api/v1/workflows/{id}`, URL —
  `<N8N_BASE_URL>/webhook/<webhookId>/webhook`. Дальше слать обычные объекты Update (`message`,
  `callback_query`) с этим заголовком. Ответы бота реальным людям при этом уходят
  по-настоящему, а фейковым — падают на `chat not found` (ставить `onError:
  continueRegularOutput` на ноду Bot API).
- **Статус:** ✅ Подтверждено на живом боте; приём применялся повторно для аналогичных проверок.

### DBG-Р6. Нода без входных элементов не выполняется — и молча обрывает всё ниже по цепочке

- **Симптом:** уведомления не ушли, ошибок нет: Code-нода отдала `[]` (нечего анализировать),
  следующая нода не запустилась, и все ноды за ней — тоже. В исполнении они просто серые.
- **Правило:** если цепочка обязана дойти до конца при любом результате, нода-фильтр всегда
  отдаёт хотя бы один элемент-заглушку (`{ problem_id: 0 }`), а принимающая сторона умеет его
  пропустить (SQL с `WHERE id = 0` → пусто → `alwaysOutputData`). На Execute Workflow —
  `alwaysOutputData: true` и `onError: continueRegularOutput`: пустой ответ или падение
  суб-сценария не должны глушить уведомления родителя; итог родитель перечитывает из базы, а не
  берёт из ответа суб-сценария.
- **Статус:** ✅ Подтверждено на реальных данных.

## ⚠️ Ошибки

### DBG-О1. Двойной ответ при пакете сообщений

- **Симптом:** при пакете сообщений (несколько подряд) бот отвечает дважды.
- **Причина:** Buffer Upsert стоит **после** Merge — видит только свои данные, не весь пакет.
- **Лечение:** перенести Buffer Upsert **до** каждого Wait.

### DBG-О2. Telegram-trigger webhook нельзя дёрнуть curl-ом — секрет

- **Симптом:** попытка симулировать апдейт Telegram через
  `curl -X POST <N8N_BASE_URL>/webhook/<webhookId>/webhook -d '{...}'` → **HTTP 403**
  `{"message":"Provided secret is not valid"}`.
- **Причина:** n8n Telegram Trigger регистрирует webhook с секретным `secret_token`; Telegram
  шлёт его в заголовке `X-Telegram-Bot-Api-Secret-Token`. Без верного секрета (а он не отдаётся
  наружу) запрос отклоняется. Это не баг — защита от поддельных апдейтов.
- **Лечение:** боты на Telegram Trigger тестировать **только живым ботом** (реальное
  сообщение/кнопка). Для отладки последней мили без полного прогона — отдельный sandbox с
  обычным `Webhook`-узлом (без секрета), который curl дёргает (DBG-Р1). Симулировать сам
  Telegram Trigger curl-ом нельзя.

### DBG-О3. Traefik стартует «running», но не слушает порт — контейнер создан в момент конфликта портов

- **Симптом:** `docker compose up -d` после конфликта портов (напр. «address already in use») →
  устраняешь конфликт → повторный `up -d` пишет «Container traefik Started», статус `running`,
  но `docker port <container>` пустой, `curl` до 80/443 падает `Connection refused`.
- **Причина:** при первом (неудачном) запуске Docker уже успел **создать** контейнер traefik с
  портами до того, как упал на биндинге — контейнер остался в состоянии «Created» без реально
  применённых port-mapping. Повторный `up -d` видит существующий контейнер и просто **стартует**
  его as-is, не пересоздавая, — сами порты не переприменяются при простом `start`.
- **Лечение:** `docker compose up -d --force-recreate <service>` — пересоздаёт контейнер с нуля,
  порты применяются заново. Обычный `up -d` в этой ситуации не поможет, сколько раз ни повторяй.
- **Диагностика:** если `docker ps` показывает `Up`, но `docker port <name>` пустой и
  `ss -tlnp` не видит порт — это оно.
- **Статус:** ✅ Подтверждено (фикс применён и проверен).

### DBG-О4. Два живых n8n с одинаковыми активными воркфлоу — schedule-триггеры дублируются независимо от DNS/маршрутизации

- **Симптом:** после переезда на новый сервер (DNS уже переключён) воркфлоу с
  **cron/Schedule Trigger** внезапно падает с ошибкой на новом сервере в тот же момент, когда на
  старом всё прошло успешно.
- **Причина:** cron/schedule-триггеры тикают **внутри каждого инстанса n8n независимо** — они не
  проходят через домен/реверс-прокси/DNS вообще. Если старый сервер не остановлен после переезда
  (данные восстановлены, воркфлоу активны на обоих) — оба инстанса дёргают один и тот же тик
  одновременно и оба пытаются обработать одну и ту же «созревшую» запись во внешнем состоянии
  (очередь, БД, внешний API) → гонка/дубль/конфликт.
- **Отличие от вебхуков:** вебхук-триггеры маршрутизируются через реверс-прокси (напр. Traefik)
  по домену — там DNS решает, какой сервер получит запрос. Schedule-триггеры это не спасает.
- **Лечение:** при любом переезде сервера с n8n — **остановить (не обязательно удалить)
  n8n/n8n-worker на старом сервере** сразу после подтверждения, что новый полностью рабочий, а
  не держать оба живыми «на всякий случай». Если нужно параллельно тестировать — деактивировать
  schedule-воркфлоу на одном из двух инстансов вручную на время проверки.
- **Статус:** ⚠️ Открытый риск, пока старый сервер полностью не остановлен.

### DBG-О5. Обработчик ошибок, пишущий лог в БД, молчит именно тогда, когда нужнее всего

- **Симптом:** связь с облачной БД пропала на минуту, упали несколько сценариев — и ни одного
  уведомления не пришло. Более того, сам обработчик ошибок в эту минуту упал трижды. Инцидент
  прошёл незамеченным; нашёлся только потому, что владелец случайно заглянул в список
  исполнений.
- **Причина:** цепочка была `Error Trigger → Prepare Error → Log Incident (Postgres) → Notify
  Admin (Telegram)`. Запись инцидента в БД стояла **перед** отправкой сообщения. Пока БД жива,
  разницы нет. Но самый частый повод для срабатывания обработчика — как раз недоступность БД, и
  тогда он падает на первом же шаге, не дойдя до уведомления.
- **Лечение:** `onError: continueRegularOutput` на ноде записи лога (+ повтор 5×5 с). Лог
  теперь необязателен: не удалось записать — сообщение всё равно уходит. Порядок нод менять не
  понадобилось, потому что Telegram-нода берёт данные из `Prepare Error`, а не из результата
  записи.
- **Как проверено:** копия обработчика с заведомо падающим SQL (`SELECT * FROM
  no_such_table_xyz`). Нода лога вернула ошибку как данные, `Notify Admin` отработал и сообщение
  доставлено (`message_id` получен). До правки цепочка на этом месте обрывалась.
- **Общее правило:** уведомитель не должен зависеть ни от чего, что способно упасть вместе с
  наблюдаемой системой. Всё, что в нём не является собственно отправкой сообщения, —
  необязательный шаг: либо после отправки, либо с проглатыванием ошибки. Иначе выходит
  наблюдатель, который слепнет ровно в момент аварии.
- **Проверка для любого обработчика ошибок:** мысленно отключить БД, сеть, внешний API — и
  посмотреть, дойдёт ли сообщение. Если нет — переставить или развязать.
- **Статус:** ✅ Проверено на копии.

### DBG-О6. `n8n execute` из контейнера не запускает сценарий с Schedule Trigger и конфликтует с боевым инстансом за порт раннера

- **Симптом:** `docker exec <n8n> n8n execute --id=<id>` → `n8n Task Broker's port 5679 is
  already in use` (второй процесс n8n в том же контейнере). С `N8N_RUNNERS_BROKER_PORT=5680`
  стартует, но падает: `Missing node to start execution — workflow must contain an Execute
  Workflow Trigger` — в 2.x CLI стартует только с Manual / Execute Workflow Trigger, расписание
  он не «нажимает».
- **Что делать:** не тратить время на CLI — проверять в боевом рантайме, см. DBG-Р4.
- **Статус:** ✅ Подтверждено.

### DBG-О7. Code-нода режет текст ошибки до части после двоеточия и дописывает `[line N]`

- **Симптом:** `throw new Error('Проверка канала: это сообщение должно прийти')` → в Error
  Trigger `execution.error.message` = `это сообщение должно прийти [line 1]`. Всё до двоеточия
  n8n трактует как имя типа ошибки и отбрасывает.
- **Правило:** в тексте `throw` не начинать с «Метка: …» — писать тире или скобки; в
  обработчике ошибок при желании добирать `error.description`.
- **Статус:** ✅ Подтверждено.

### DBG-О8. В Code-ноде под task runner закрыты `require('crypto')`, `$env`, `process`, нет Web Crypto

- **Симптом:** `require('crypto')` → `Module 'crypto' is disallowed`; `$env.X` → `access to env
  vars denied` (`N8N_BLOCK_ENV_ACCESS_IN_NODE=true`); `process` не определён;
  `globalThis.crypto.subtle` — `undefined`. Есть `Buffer`.
- **Правило:** на таком контуре HMAC/SHA-256 писать на чистом JS (готовая реализация уже
  встречалась в ноде авторизации Mini App API и переиспользовалась в другом контуре). Секреты в
  ноду — плейсхолдером через скрипт выкладки, не через `$env`. Проверять доступность модулей
  временным вебхук-сценарием, а не гадать: набор зависит от `NODE_FUNCTION_ALLOW_BUILTIN` и
  режима раннера.
- **Статус:** ✅ Подтверждено.
