## ⚠️ Ошибки

### SET-О1. Set typeVersion 3.4 — strict-режим типов

- **Симптом:** Set-нода падает с `'field' expects a number but we got 'expression_string'`.
- **Причина:** в typeVersion 3.4 строгий режим. Поле, значение которого — expression (`=...`),
  обязано иметь `"type": "string"`.
- **Лечение:** всем полям-expression ставить `"type": "string"`. Для констант
  `type: number/boolean` безопасен.
- **Связанное:** автоповышение typeVersion при SDK update_workflow ломает поведение — см.
  rest-api-deploy.md DEP-О2.

### SET-О2. Execute Workflow передаёт в суб СВОЙ входной item — не вставлять ноды между источником данных и вызовом

- **Симптом:** суб-воркфлоу получает не подготовленные данные, а выход последней ноды перед
  Execute Workflow (например, `{success:true}` от Telegram-уведомления) — поля undefined.
- **Причина:** Execute Workflow (passthrough) отдаёт в суб ровно те items, что пришли ему
  на вход. Вставка «уведомительной» ноды (Telegram «🚀 Публикую…») между источником данных
  и вызовом подменяет item.
- **Лечение:** уведомление и вызов суба вешать **параллельно** с одного выхода IF/источника
  (fan-out), а не цепочкой. Либо перед вызовом восстановить item через Set/expression на источник.
- **Источник:** основной воркфлоу продукта (инцидент 10.06.2026); фикс — параллельные ветки
  от IF-проверки готовности.
- **Статус:** ⚠️ Подтверждено на практике.

### SET-О3. Code-нода (Run Once for All Items), отдающая один item, молча теряет остальные

- **Симптом:** триггер/выборка отдаёт N items (напр. Postgres вернул 5 строк), а downstream
  обрабатывает **только первый** — остальные пропадают без ошибки. На практике: воркфлоу
  по крону (раз в час) слал проактив/напоминания **только одному** из очереди за тик →
  накопление и **опоздание до суток** (инцидент 25.06.2026).
- **Причина:** Code-нода в режиме *Run Once for All Items* выполняется один раз. Код вида
  `const x=$('Node').item.json; … return [{json:…}]` берёт **первый** item (`.item` = первый
  при All-Items) и возвращает массив из одного элемента — n8n считает это полным выходом ноды.
  Цепочка дальше идёт уже с 1 элементом.
- **Лечение:** обрабатывать весь вход — цикл по `$input.all()` (или `items`), сопоставляя
  с другими нодами через `$('Node').all()[i]` по индексу, и `return out` массивом из N
  элементов. Каждому пушу проставлять `pairedItem:{item:i}`, чтобы downstream `$('X').item`
  корректно резолвился. Невалидные — `continue` (не `return []`). Альтернатива — режим
  *Run Once for Each Item* (тогда `return {json:…}` на каждый, но «пропуск» элемента сложнее).
- **Проверка fan-out без побочек:** временный воркфлоу-мок (Webhook → Code-моки с именами
  как в проде → тестируемые Code-ноды → Respond allIncomingItems), прогнать точно
  задеплоенный код, удалить после.
- **Источник:** воркфлоу проактивных уведомлений (Code-ноды `Build Prompt`, `Build Send+Book`);
  журнал изменений проекта.
- **Статус:** ⚠️ Подтверждено разбором executions + изолированным тестом (боевая проверка
  на многокандидатной очереди — утренний тик).

### SET-О4. `$('Узел').item` рвётся через промежуточные ноды при ≥2 item — «Multiple matches found» всплывает только с ростом данных

- **Симптом:** воркфлоу месяцами работал, упал с `Multiple matches found` на узле с
  выражением `$('Дальний узел').item.json.X`, как только item'ов стало два (второй
  получатель/строка).
- **Причина:** `.item` — спаренная (paired-item) трассировка «мой текущий item ← его предок
  в том узле». Промежуточные ноды (напр. Postgres executeQuery) не всегда сохраняют парность;
  при 1 item неоднозначности нет и всё «работает», при ≥2 n8n не может выбрать предка →
  ошибка. Классическая мина замедленного действия: тесты на одном пользователе её не ловят.
- **Лечение:** данные для узла-потребителя вести **его собственным входом** (`$json.X`):
  фан-аут от узла-источника напрямую (`Source → A` и `Source → B` параллельно), а не через
  цепочку `Source → A → B` с кросс-ссылкой `.item`. Если фан-аут не подходит —
  `$('Source').all()[$itemIndex]` при гарантированном 1:1 порядке, или `.first()` когда item
  заведомо один.
- **Источник:** `<workflow_name>` узел Ping (продукт-коуч), первый запуск с 2 получателями
  отчёта, 05.07.2026. Отчёты в БД уцелели (Store — upsert), потерялся только пуш; досланы
  вручную.
- **Статус:** ⚠️ Грабля (фикс подтверждён доставкой пингов).

### SET-О5. Лукап-нода (HTTP/Postgres) с `executeOnce` в основной линии схлопывает поток → per-item ноды ниже отрабатывают ОДИН раз

- **Симптом:** «отчёт без информации» — IG-охват заполнился только у **1 поста из 16**,
  у остальных пусто.
- **Причина:** цепочка была `Посты(16) → Страница канала[executeOnce] → Токен IG[executeOnce]
  → IG insights(per-post) → …`. `executeOnce` (и любая лукап-нода, отдающая 1 item)
  **обрезает поток до 1 item**, поэтому `IG insights`, который должен бежать по каждому
  посту, получил 1 вход → отработал 1 раз (по первому посту). Данные по остальным 15 не
  запросились.
- **Решение:** одноразовые лукапы (страница `t.me/s`, токен) ставить **в начало линии**,
  до ноды, разворачивающей поток (SELECT постов), и обращаться к ним **референсом**
  `$('Токен IG').first().json.token` / `$('Страница канала').first().json.data`. Тогда
  per-item нода (`IG insights`) кормится 16 постами и бежит 16 раз, а лукапы доступны по
  имени.
  Порядок: `Токен IG(1) → Страница(1) → Посты(16, SELECT игнорит вход) → IF → IG insights(16,
  token/page референсами) → Сводка(1)`.
- **Правило:** нода, которой нужно отработать **по каждому элементу**, должна получать
  полный поток. Всё, что фетчится **однократно**, — либо в начало линии (референсом), либо
  в отдельную ветку; НЕ ставить «одноразовое» между источником списка и per-item-обработкой.
- **Связь:** родственно SET-О2 (Execute Workflow передаёт свой item), SET-О4 (`.item`
  рвётся на ≥2 items).
- **Источник:** продукт-публикатор — <workflow_name> (дайджест), 19.07.2026.
- **Статус:** ✅ Исправлено (песочница: IG-охват по 15/16 постам).

### SET-О6. Code-нода с `executeOnce` видит только первый элемент: `$input.all()` возвращает один из N ⚠️

- **Симптом:** рассылка ушла троим (Telegram-нода — 3 элемента, у каждого свой `message_id`),
  а Code-нода «Собрать» после неё сохранила только первый чат. Кнопки «Принял/Закрыть» правили
  сообщение только у первого адресата; недоставку второму и третьему нода не видела, повтор
  не срабатывал. Статус исполнения — success.
- **Причина:** у Code-ноды в режиме *Run Once for All Items* стоял флаг `executeOnce: true`
  («Execute Once» в настройках ноды). Флаг не «запустить код один раз» — код и так выполняется
  один раз в этом режиме, — а «передать ноде только первый входной элемент». Внутри
  `$input.all()` — массив из одного элемента; `$('Другая нода').all()` при этом возвращает все,
  поэтому ошибка маскируется: сверка по индексу даёт `undefined` без исключения.
- **Решение:** у Code-нод, которые читают `$input.all()`, флаг `executeOnce` не ставить никогда.
  Он нужен только нодам-лукапам без входной выборки (Postgres/HTTP с одним запросом) — и там
  с оглядкой на SET-О5.
- **Как искать:** пройти JSON сценариев и отметить ноды `type == code && executeOnce &&
  '$input.all()' in jsCode` (за 15.09.2026 нашлось три: «Собрать» и «Убрать записанные» —
  в одном воркфлоу (`<workflow_name>`), «Итог» — в другом (эскалация)).
- **Почему не поймали тестом:** на момент прогона адресат был один — один элемент ведёт себя
  одинаково с флагом и без. Проверять рассылки минимум на двух получателях.
- **Источник:** корпоративный клиент, `<workflow_name>`, 14–15.09.2026.
- **Статус:** ⚠️ Зафиксировано 15.09.2026.
