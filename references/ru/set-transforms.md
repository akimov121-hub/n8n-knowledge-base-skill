## ⚠️ Ошибки

### SET-О1. Set typeVersion 3.4 — strict-режим типов

- **Симптом:** Set-нода падает с `'field' expects a number but we got 'expression_string'`.
- **Причина:** в typeVersion 3.4 строгий режим. Поле, значение которого — expression (`=...`),
  обязано иметь `"type": "string"`.
- **Лечение:** всем полям-expression ставить `"type": "string"`. Для констант
  `type: number/boolean` безопасен.
- **Связанное:** автоповышение typeVersion при SDK update_workflow ломает поведение — см.
  rest-api-deploy.md DEP-О2.

### SET-О2. Execute Workflow передаёт в суб СВОЙ входной item — не вставлять ноды между источником данных и вызовом

- **Симптом:** суб-воркфлоу получает не подготовленные данные, а выход последней ноды перед
  Execute Workflow (например, `{success:true}` от Telegram-уведомления) — поля undefined.
- **Причина:** Execute Workflow (passthrough) отдаёт в суб ровно те items, что пришли ему
  на вход. Вставка «уведомительной» ноды (Telegram «🚀 Публикую…») между источником данных
  и вызовом подменяет item.
- **Лечение:** уведомление и вызов суба вешать **параллельно** с одного выхода IF/источника
  (fan-out), а не цепочкой. Либо перед вызовом восстановить item через Set/expression на источник.
- **Источник:** основной воркфлоу продукта (инцидент 10.06.2026); фикс — параллельные ветки
  от IF-проверки готовности.
- **Статус:** ⚠️ Подтверждено на практике.

### SET-О3. Code-нода (Run Once for All Items), отдающая один item, молча теряет остальные

- **Симптом:** триггер/выборка отдаёт N items (напр. Postgres вернул 5 строк), а downstream
  обрабатывает **только первый** — остальные пропадают без ошибки. На практике: воркфлоу
  по крону (раз в час) слал проактив/напоминания **только одному** из очереди за тик →
  накопление и **опоздание до суток** (инцидент 25.06.2026).
- **Причина:** Code-нода в режиме *Run Once for All Items* выполняется один раз. Код вида
  `const x=$('Node').item.json; … return [{json:…}]` берёт **первый** item (`.item` = первый
  при All-Items) и возвращает массив из одного элемента — n8n считает это полным выходом ноды.
  Цепочка дальше идёт уже с 1 элементом.
- **Лечение:** обрабатывать весь вход — цикл по `$input.all()` (или `items`), сопоставляя
  с другими нодами через `$('Node').all()[i]` по индексу, и `return out` массивом из N
  элементов. Каждому пушу проставлять `pairedItem:{item:i}`, чтобы downstream `$('X').item`
  корректно резолвился. Невалидные — `continue` (не `return []`). Альтернатива — режим
  *Run Once for Each Item* (тогда `return {json:…}` на каждый, но «пропуск» элемента сложнее).
- **Проверка fan-out без побочек:** временный воркфлоу-мок (Webhook → Code-моки с именами
  как в проде → тестируемые Code-ноды → Respond allIncomingItems), прогнать точно
  задеплоенный код, удалить после.
- **Источник:** воркфлоу проактивных уведомлений (Code-ноды `Build Prompt`, `Build Send+Book`);
  журнал изменений проекта.
- **Статус:** ⚠️ Подтверждено разбором executions + изолированным тестом (боевая проверка
  на многокандидатной очереди — утренний тик).
