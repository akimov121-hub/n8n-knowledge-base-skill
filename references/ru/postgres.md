## ✅ Решения

### PG-Р1. Контроль типа значения в SQL — встраивать `{{ Number(...) }}` прямо в текст запроса

- **Контекст:** нужно подставить в запрос числовое значение (id, message_id) так, чтобы оно
  ушло в БД **числом**, а не строкой.
- **Факт (проверено):** cross-node ссылки в `queryReplacement` **вычисляются** —
  `$('Нода').first().json.поле` резолвится нормально. То есть заводить значение через
  `queryReplacement` с cross-node ref — рабочий путь.
- **Нюанс:** `queryReplacement` передаёт значение как параметр `$1`, и эвалуированный
  результат часто уходит **строкой**. Если целевая колонка `bigint`/`numeric` — это даёт
  ошибку (см. PG-О1). Чтобы значение гарантированно пошло числом, два пути:
  1. Обернуть в `Number(...)` прямо в выражении `queryReplacement`.
  2. Встроить числовой литерал прямо в текст SQL:

```sql
VALUES ({{ Number($('Telegram Trigger').first().json.message.message_id) }})
```

Статус: ✅ Подтверждено.

### PG-Р2. Произвольный SQL / DDL через временный webhook-воркфлоу

- **Контекст:** публичный REST API n8n не умеет выполнять произвольный SQL; ноды Postgres
  Chat Memory создают таблицы лениво (при первом сообщении); нужно создать таблицу заранее,
  посмотреть схему, прогнать «сухой» тест перед `DELETE`, точечно заполнить справочник.
- **Решение:** одноразовый воркфлоу `Webhook (POST) → Postgres executeQuery → Respond to
  Webhook (allIncomingItems)`. Создать через `POST /api/v1/workflows`, активировать, дёрнуть
  curl-ом, прочитать результат из ответа, затем **деактивировать и удалить** (не оставлять
  активный публичный webhook — мини-риск).
- **Применения:** `CREATE TABLE`, сверка схемы (`SELECT … FROM information_schema.columns`),
  сухой прогон чистки (`SELECT count(*)` вместо `DELETE` — посмотреть, что удалится),
  наполнение справочников `INSERT`-ом с dollar-quoting (`$Q$текст$Q$`) для текстов с
  кавычками.
- **Нюанс:** имя таблицы можно подставлять выражением прямо в текст `executeQuery`
  (`{{ $json.table }}`) — n8n резолвит выражение до отправки в БД. Безопасно, пока имя
  берётся из своего контролируемого списка, а не из пользовательского ввода.

Статус: ✅ Подтверждено.

### PG-Р3. Вставка в наименьший свободный `id` (gap-fill, переиспользование номеров)

- **Контекст:** пользователю показывается `id` записи как «номер» (память бота, напоминания,
  любой личный список). При обычном `serial` после удаления остаются дыры, а новые записи
  уходят в конец. Хочется, чтобы номера шли без дыр и **освободившийся номер занимала
  следующая новая запись**.
- **Решение:** не трогать схему и не пересоздавать PK. Вместо `serial` вставлять **явный
  `id` = наименьший свободный** через `generate_series` + анти-джойн. Реальный PK при этом
  равен показываемому номеру — `delete`/`update` адресуются по нему напрямую.

```sql
INSERT INTO <table> (id, ...) VALUES (
  (SELECT COALESCE(MIN(s.n),1)
     FROM generate_series(1, COALESCE((SELECT MAX(id) FROM <table>),0)+1) s(n)
     LEFT JOIN <table> m ON m.id = s.n
    WHERE m.id IS NULL),
  ...
) RETURNING id;
```

- **Поведение:** пусто → id 1; есть {2,3,4} → новая займёт 1, потом 5; удалил середину →
  следующая новая займёт её. Существующие номера не меняются.
- **Нюансы:** скалярный подзапрос в `VALUES` видит таблицу ДО вставки — корректно. Раз всегда
  вставляем явный `id`, `serial`-счётчик не используется → коллизий нет (важно, чтобы ВСЕ
  пути вставки шли через этот паттерн). Для мультиюзера добавить `WHERE telegram_id=...` в
  обе части подзапроса.
- **Сопутствующее:** правка записи «на месте» — отдельная операция `UPDATE` по id, а не
  delete+insert (иначе номер уезжает в конец).

Статус: ✅ Подтверждено в проде.

### PG-Р4. Идемпотентность действия через атомарный захват статуса (защита от двойного нажатия кнопки)

- **Контекст:** inline-кнопка, запускающая необратимое действие (публикация, списание,
  отправка), при двойном нажатии порождает **два параллельных прогона**. Оба читают статус
  «готово к действию» раньше, чем первый его сменит → действие выполняется дважды (двойной
  пост и т.п.).
- **Решение:** не «SELECT статус → IF», а **атомарный UPDATE с условием** на статусной строке:

```sql
UPDATE drafts SET stage='processing', updated_at=now()
WHERE chat_id=<chat_id> AND stage='await_review'
RETURNING <нужные колонки>;
```

  Postgres сериализует конкурентные UPDATE по строке: первый флипает
  `await_review→processing` и возвращает строку, второй уже не находит `await_review` →
  0 строк. **Важно (см. PG-О2):** при 0 строк нода отдаёт НЕ 0 items, а служебный item
  `{success:true}` — поэтому защита работает только в паре с IF по статусу/ключевому полю
  (`stage='processing'` / `chat_id notEmpty`) сразу после UPDATE. Никаких таймеров/дебаунсов —
  гарантия на уровне БД + обязательный IF.
- **Нюанс:** если действие может частично упасть после захвата — статус останется
  `processing`; предусмотреть откат либо довести до финального статуса в любой ветке
  (onError continue).

Статус: ✅ Подтверждено.

### PG-Р5. Текстовые параметры через queryReplacement массивом-expression

- **Паттерн:** пользовательский текст в SQL передавать НЕ конкатенацией с эскейпом `'`→`''`,
  а параметрами `$1..$n`: в options ноды `queryReplacement` = `={{ [выражение1, выражение2, ...] }}`
  (одно expression, возвращающее массив).
- **Почему массив:** строковый comma-separated формат queryReplacement ломается на запятых
  внутри значения; массив-expression переносит запятые, кавычки, HTML и переводы строк без
  потерь.
- **Проверено на живом:** `SELECT $1::text...` + `={{ [$json.body.a, ...] }}` — значения с
  запятыми/кавычками/тегами вернулись 1:1.
- **Ограничение:** значения уходят строками — для `bigint`/`numeric` колонок по-прежнему
  встраивать `{{ Number(...) }}` литералом в SQL (PG-Р1, PG-О1).
- **Применение:** продукт-публикатор — все записи текста поста/указаний/caption.

Статус: ✅ Подтверждено.

### PG-Р6. Webhook-ответ списком/объектом — `json_agg`/scalar-subquery, гарантированно 1 строка

- **Контекст:** в Mini App API (webhook + Respond) действия типа `list`/`get` читают из БД.
  Если SELECT вернёт 0 строк — ветка может не продолжиться, и нода `Respond to Webhook` не
  сработает → **запрос виснет** на фронте (см. также неоднозначность PG-О2: 0 строк → иногда
  `{success:true}`, иногда пусто).
- **Решение:** заворачивать выборку так, чтобы нода **всегда отдавала ровно 1 строку**:
  - список → `SELECT COALESCE(json_agg(x), '[]'::json) AS __list FROM (SELECT ... ) x;` —
    пусто → `[]`, иначе массив.
  - объект → `SELECT COALESCE((SELECT to_jsonb(t) FROM (SELECT ...) t), '{}'::jsonb) AS __obj;` —
    нет записи → `{}`.

  Дальше Code-нода нормализует (`if(typeof v==='string') JSON.parse`), Respond отдаёт
  массив/объект. Бонус: `bigint` внутри `json_agg`/`to_jsonb` сериализуется **числом** (не
  строкой) — чинит epoch-ms времена для фронта.

Статус: ✅ Подтверждено.

## ⚠️ Ошибки

### PG-О1. `invalid input syntax for type bigint`

- **Симптом:** Postgres executeQuery падает с `invalid input syntax for type bigint`.
- **Причина:** `queryReplacement` передаёт эвалуированное значение как параметр `$1`
  **строкой**; если колонка `bigint`/`numeric`, а строка пустая или нечисловая — Postgres
  не приводит её и падает. (Причина именно в типе значения, а не в том, что cross-node
  выражение «не вычисляется» — оно вычисляется, см. PG-Р1.)
- **Лечение:** обернуть значение в `Number(...)` в `queryReplacement` либо встроить числовой
  литерал прямо в SQL через `{{ Number(...) }}`. Заодно гарантировать, что значение непустое.

### PG-О2. executeQuery при 0 строк отдаёт item {success:true}, а не 0 items

- **Симптом:** downstream-ноды после Postgres-ноды выполняются, хотя запрос
  (UPDATE...RETURNING / SELECT) не вернул ни одной строки; в item лежит `{"success": true}`
  без полей запроса. Если за нодой стоит Execute Workflow — суб-воркфлоу вызывается с этим
  мусорным item (`image_url=undefined` и т.п.).
- **Причина:** n8n Postgres executeQuery при пустом результате эмитит служебный item
  `{success:true}` — рассчитывать на «0 строк → ветка не выполнится» нельзя.
- **Лечение:** после каждого «может вернуть 0 строк» запроса — IF-guard по ключевому полю
  (`{{ $json.chat_id }}` notEmpty или проверка статуса), и только потом действие.
- **Статус:** ⚠️ Подтверждено на практике.

### PG-О3. Dollar-quoting `$tag$…$tag$` со значением-числом ломает сканер параметров n8n

- **Симптом:** Postgres-нода падает `Variable $<большое число> exceeds supported maximum of $100000`,
  хотя в запросе нет такого номера параметра. Пример: вставка Telegram bot-token
  `<BOT_TOKEN>` через `VALUES ('bot_token', $tok$<BOT_TOKEN>$tok$)`.
- **Причина:** n8n сканирует SQL на плейсхолдеры `$N` (queryReplacement) **до** отправки в
  Postgres и не понимает dollar-quoting. Закрывающий `$` тега + цифры значения
  (`…$tok$<цифры токена>`) читаются как `$<число>` → «номер параметра» вне диапазона.
- **Лечение:** значения **никогда** не вставлять dollar-quoting'ом — передавать нативным
  параметром `$1` через `options.queryReplacement` (см. PG-Р5). Особенно критично для
  значений, начинающихся с цифр (id, токены).
- **Статус:** ⚠️ Подтверждено на практике.

### PG-О4. Многооператорный SQL как n8n-выражение (с `{{ }}`) → «invalid syntax»

- **Симптом:** Postgres-нода с многооператорным запросом (несколько `;`), где значения
  встроены через `{{ … }}` (т.е. весь текст запроса стал n8n-выражением с ведущим `=`),
  падает с `invalid syntax` ещё до Postgres. Одиночный оператор с тем же `{{ }}` при этом
  работает.
- **Причина:** когда весь SQL — одно n8n-выражение, парсер выражений спотыкается на сложном
  многооператорном тексте (особенно с regex/спецсимволами внутри `{{ }}`). Это ошибка движка
  выражений n8n, не Postgres.
- **Лечение:** **один оператор — одна нода** + значения нативными параметрами `$1`
  (queryReplacement); `{{ }}` оставлять только в отдельных полях (params / chatId / text
  Telegram-ноды), но НЕ в тексте SQL. Многошаговую операцию (UPSERT + пометка + лог + выборка)
  разложить в цепочку нод. Для регулярок/санитайзинга — отдельная Code-нода (Prep), а SQL
  ссылается на готовые чистые значения.
- **Статус:** ✅ Подтверждено (после разбивки на одиночные операторы всё заработало;
  smoke-цикл grant/revoke/add/decline зелёный).

### PG-О5. executeQuery с многооператорным SQL возвращает результат ПЕРВОГО оператора, не последнего

- **Симптом:** в Postgres-ноде один запрос из нескольких операторов
  (`INSERT…; UPDATE…; SELECT…;`). Все операторы **выполняются** (записи проходят), но в
  выходной item ноды попадает результат **первого** оператора. Нода, которая ниже читает
  `$('Эта нода').first().json.<поле из последнего SELECT>`, получает `undefined`. Пример:
  grant-нода (3 write + финальный `SELECT bot_name`), сообщение рендерится как «боту
  «undefined»».
- **Проверка (read-only):** `SELECT 'a' AS first_stmt; SELECT 'b' AS second;` → нода вернула
  `{first_stmt:'a'}`.
- **Лечение:** значение, которое нужно downstream, доставать **отдельной нодой** (одиночный
  SELECT) — её результат корректен. Многооператорные write-и оставлять как есть, если их
  результат не читается. В Mini App API это и так разнесено по нодам (Grant SQL отдельно от
  Grant BotName).
- **Связь:** усиливает PG-Р6 (одна нода = один нужный результат) и PG-О4.
- **Статус:** ✅ Подтверждено (read-only тест + разнос на ноды).

## ✅ Решения (продолжение)

### PG-Р7. Черновик «одна строка на пользователя» — при старте нового элемента обнулять перенесённые поля

- **Контекст:** состояние мастера (черновик поста) хранится одной строкой `pub_drafts` на
  `user_id` (UPSERT `ON CONFLICT (user_id)`). Та же строка переиспользуется для следующего
  поста.
- **Грабля:** UPSERT при генерации текста НОВОГО поста обновлял `mode/idea/header/post/stage`,
  но **не трогал производные поля прошлого поста** (`image_url`, `ig_caption`). Итог: новый
  пост наследовал старую обложку/подпись; фронт (поллинг `draft/get`) подхватывал старую
  картинку и предлагал «Перегенерировать» вместо создания новой.
- **Решение:** в `ON CONFLICT DO UPDATE` для нового элемента **явно обнулять все
  перенесённые/производные поля**:
  `... SET mode=$1, idea=$2, header=$3, post=$4, stage='text', image_url=NULL, ig_caption=NULL, updated_at=now()`.
  Правило общее: при reuse строки-состояния новый «жизненный цикл» должен сбрасывать всё, что
  относилось к предыдущему, а не только перезаписываемые поля.
- **Защита на клиенте (доп.):** мирор на фронте тоже чистить при старте
  (`S.draft.imageUrl=''; igCaption=''`), иначе резистентный поллинг-вотчер повторно подхватит
  несвежее.

Статус: ✅ Подтверждено.

### PG-Р8. Свободный merge JSONB (`data || EXCLUDED.data`) — новые метрики фронта без миграций схемы

- **Контекст:** фронт (Mini App «Дневник») пишет дневные метрики; набор ключей растёт от
  версии к версии (добавились `stress`, `anxiety`, `focus`, `sleep_quality`,
  `meditation_min`, `reflection`-объект, `nutrition` стал числом). Хранить каждый ключ
  отдельной колонкой → миграция на каждую новую метрику.
- **Решение:** держать метрики одной JSONB-колонкой `data` и в UPSERT делать **частичный
  merge**: `INSERT … ON CONFLICT (telegram_id, day) DO UPDATE SET data = daily_checkin.data || EXCLUDED.data`.
  Оператор `||` для jsonb — поверхностное слияние: новые/изменённые ключи перезаписываются,
  старые сохраняются. `checkin/history` отдаёт весь `data` целиком → новые ключи возвращаются
  на фронт без правок бэка.
- **Что это даёт:** добавление метрики на фронте НЕ требует ни миграции БД, ни правки
  воркфлоу — только проверка. Валидация имени ключа — лёгким regex (`^[a-z][a-z0-9_]{0,40}$`),
  без жёсткого whitelist. Значения любых типов (число/скаляр/вложенный объект) проходят.
- **Границы:** `||` сливает только верхний уровень — вложенный объект (`reflection`)
  перезаписывается целиком, не мержится по-ключам. Если нужен глубокий merge — `jsonb_set`
  или `jsonb_deep_merge`-функция. Минус подхода — нет схемы на уровне БД (типы/обязательность
  ключей не гарантируются), поэтому критичные/индексируемые поля держать отдельными
  колонками, а в JSONB — только «расширяемый хвост» метрик.

Статус: ✅ Подтверждено.

### PG-Р9. Идемпотентность планирования: фильтр стадии при вставке из переиспользуемой строки-черновика

- **Симптом:** один и тот же пост появился в очереди дважды (две строки `publisher_queue`,
  одинаковый контент и `publish_at`).
- **Причина:** экшен `publish/schedule` вставлял строку, читая черновик
  `... FROM pub_drafts WHERE post<>'' AND image_url<>''` — **без проверки стадии**. После
  первого планирования стадия → `queued`, но `post`/`image_url` остаются → повторный вызов
  (двойной тап на кнопке времени / ретрай / редоставка вебхука) снова проходит фильтр и
  вставляет дубль. Один вызов = одна строка (`INSERT ... SELECT FROM src`), значит дубль =
  два вызова.
- **Решение:** добавить в `src` фильтр активной стадии — вставлять только из НЕ-завершённого
  черновика: `... AND stage IN ('idea','text','image','preview')`. После первого планирования
  (`stage='queued'`) повторный вызов находит 0 строк в `src` → `INSERT ... SELECT` ничего не
  вставляет → идемпотентно. Правило общее: **любая «однократная» вставка из строки-состояния,
  которая остаётся жить, должна гейтиться по стадии/флагу «уже обработано»**, иначе повтор
  запроса плодит дубли.
- **Доп. защита на клиенте:** флаг in-flight против двойного тапа — глушит дубль ещё до
  бэкенда. Полную защиту от гонки даёт ещё и уникальный индекс, но stage-фильтр закрывает
  реальный кейс (последовательный двойной тап).

Статус: ✅ Подтверждено.
